# PispIAr — A-21B.6c.1 · Prueba local aislada de migraciones

## Propósito y alcance

Validar que la imagen `migrator` incorporada por PR #73 puede aplicar el historial Prisma completo sobre una base PostgreSQL 16 + pgvector nueva y repetir `prisma migrate deploy` sin cambios pendientes.

La prueba se ejecutó el 12 de noviembre de 2026 desde `develop` en el commit `a8c40cc` (merge de PR #73), dentro de Docker Desktop con contexto `desktop-linux`. No se utilizaron Compose, servicios existentes, puertos host, named volumes, credenciales compartidas ni infraestructura cloud.

## Script repetible

El script [`scripts/deploy/test-prisma-migrations.ps1`](../../scripts/deploy/test-prisma-migrations.ps1):

- exige Docker Desktop local con engine Linux;
- calcula las migraciones esperadas a partir de los directorios de `apps/api/prisma/migrations` y exige un `migration.sql` en cada uno;
- genera nombres, usuario, base y contraseña aleatorios por corrida, sin imprimirlos;
- construye el target `migrator` del commit actual;
- crea una red Docker dedicada e interna;
- inicia un contenedor nuevo `pgvector/pgvector:pg16` sin puertos publicados y con `/var/lib/postgresql/data` en `tmpfs`;
- comprueba que la red tenga sólo el PostgreSQL de la prueba, que la base pertenezca al rol temporal y que `public` esté vacío, sin `_prisma_migrations`;
- aplica `prisma migrate deploy`, verifica el schema y ejecuta el mismo comando por segunda vez;
- elimina en `finally` solamente contenedores, red e imagen cuyo label de ownership coincide con la corrida.

Todos los valores sensibles se pasan al proceso Docker mediante variables de entorno en memoria. El script no imprime credenciales ni la conexión completa.

## Comando ejecutado

Desde la raíz del repositorio:

```powershell
pwsh -NoProfile -File scripts/deploy/test-prisma-migrations.ps1
```

No se ejecutaron `migrate reset`, `migrate dev`, `db push`, seeds ni comandos contra bases existentes.

## Incidentes encontrados durante el desarrollo del test

Se conservaron los controles y se corrigieron las verificaciones; no se alteraron migraciones ni schema:

1. La primera corrida abortó durante el preflight porque Docker Desktop expone el `tmpfs` en `HostConfig.Tmpfs`, no como se había consultado inicialmente. No llegó a ejecutar migraciones. La limpieza por label quedó confirmada.
2. Dos corridas posteriores aplicaron las migraciones, pero las consultas de inspección fallaron al concatenar campos internos PostgreSQL de tipo `"char"` (`contype` y `attgenerated`). Se agregaron casts explícitos a texto. Ambas bases eran descartables y la limpieza por label quedó confirmada.
3. La corrida final completó migración, verificación, idempotencia y limpieza con resultado OK.

Ningún fallo se resolvió omitiendo un control de seguridad o de schema.

- Contexto obligatorio `desktop-linux`; servidor reportado como Linux/Docker Desktop.
- Red única, dedicada e `--internal`.
- PostgreSQL nuevo con credenciales y database aleatorias.
- Cero publicaciones de puertos.

- Base y `_prisma_migrations` inexistentes/vacíos antes del primer deploy.
- Recursos etiquetados con `io.pispiar.task=A-21B.6c.1` y un identificador único de ownership.

## Limitaciones y riesgos pendientes

- Una base vacía no permite evaluar duración de locks, reescrituras, tamaño de índices ni seguridad de migración con datos de volumen productivo.
- La prueba no valida drift, duplicados o incompatibilidades existentes en una base real.
- El tag `pgvector/pgvector:pg16` no fija por sí solo una versión/digest productivo de pgvector.
- No se validaron proveedor cloud, TLS, red privada, permisos mínimos separados, backup/restauración ni procedimiento de forward-fix.
- Los tiempos medidos localmente no deben usarse para definir una ventana productiva.
