## 1. Objetivo y límites

Definir una topología candidata que permita demostrar PispIAr con autenticación real y datos persistentes mediante HTTPS, a partir de la infraestructura que el código efectivamente necesita. Identificar decisiones y dependencias antes de A-21b (implementación cloud). Se trabaja **solo sobre documentación**.

No se crearán cuentas, instancias, buckets, bases, subdominios, certificados ni claves. No se cambiarán endpoints, CI, código o configuración local; tampoco se publicarán secretos.

## 3. Topología candidata de referencia (plan v2.1, NO aprobada)

```text
NAVEGADOR
  | HTTPS 443 — mismo origen para interfaz y llamadas /api/**
  v
WEB NEXT.JS — hosting a acordar (ejemplo: Vercel)
  | rewrite servidor: /api/** -> API_URL/api/**, por HTTPS
  v
API NESTJS — hosting a acordar (ejemplo: EC2 con proxy TLS)
  |\
  | +--> POSTGRESQL + pgvector — proveedor a acordar
  | |     conexión cifrada y credenciales privadas
  | +--> REDIS — red privada, sin puerto público
  | +--> S3 o compatible — bucket privado, IAM mínimo
  | +--> PROVEEDOR IA — solo si la demo incluye RAG
  |
  +----> Logs y supervisión sin secretos, administrados por el equipo
```

Las URLs, DNS, regiones, proveedores concretos, costos y personas responsables están **pendientes**. Ningún ejemplo anterior es un recurso real confirmado.

### Recorrido funcional esperado

1. El navegador abre la aplicación por `https://<dominio-web-acordado>`.
2. La web llama `/api/...` de forma relativa; Next.js reenvía hacia la API mediante `API_URL` **en el servidor**.
3. La API valida identidad y permisos contra el estado vigente de PostgreSQL. Redis aplica las restricciones que dependen de él, sin permitir acceso por defecto ante falla.
4. Los documentos se persisten en almacenamiento de objetos privado; la descarga se resuelve con el mecanismo autorizado por el backend. Revisar la seguridad de las URLs temporales y, si corresponde, CORS para descargas directas.
5. El proveedor de IA se conecta únicamente si el alcance de demo lo requiere y con credenciales manejadas fuera del repositorio. Antes de enviar fragmentos al modelo se aplican filtros de autorización.

## 4. Seguridad mínima y delimitación de red

| Superficie | Regla propuesta | Evidencia requerida para aprobar |
|---|---|---|
| Entrada pública | HTTPS 443 para interfaz y API; HTTP 80 solo para redirección/control de certificado si aplica | DNS, certificado válido, prueba desde otra red |
| PostgreSQL | No exponer puerto `5432` a Internet; acceso restringido de API, TLS según servicio | Reglas de firewall/red y prueba de conexión cifrada |
| Redis | Nunca publicar `6379` en Internet; credenciales/red privada según proveedor | Reglas de acceso y prueba de rate limiting |
| S3 / objetos | Bucket privado, privilegios mínimos; no publicar credenciales ni archivos por defecto | Política IAM, configuración del bucket y prueba de descarga autorizada |
| Refresh cookie | `HttpOnly`, `Secure`, `SameSite`, `Path=/api/auth`; verificar tránsito real por rewrite HTTPS | Captura sanitizada de atributos, login/refresh/logout de navegador |
| Secrets | Variables en secret manager o panel restringido; jamás en Git, PR, logs, capturas o imagen Docker | Checklist de variables por entorno, sin valores |
| Migraciones | En cloud usar procedimiento revisado, `prisma migrate deploy`; **nunca** `migrate reset` ni seed de desarrollo | Estado de migraciones, copia de seguridad/rollback y verificación de índices |
| Disponibilidad | Reinicio, observabilidad mínima, límites de recursos y plan de apagado | Responsable operativo y procedimiento probado |

La configuración Docker de desarrollo del repositorio expone puertos locales; **no debe copiarse tal cual a producción**. El cambio local del puerto `5433` es exclusivo del equipo de desarrollo y está fuera del alcance de este documento.

## 5. Alternativas para decisión del equipo

| Alternativa | Composición tentativa | Ventaja buscada | Riesgo / trade-off principal | Estado |
|---|---|---|---|---|
| A — Separada (referencia del plan) | Next.js en Vercel; API en EC2 con HTTPS; PostgreSQL Supabase con pgvector; Redis privado; S3 o compatible | Separar web, API y estado, reutilizar adaptadores actuales | Más cuentas, red/egress, costos y coordinación operativa | **Por decidir** |
| B — Infraestructura concentrada | Web/API/Redis y eventualmente PostgreSQL en VPS/VM, objetos persistentes compatibles con S3 | Menos proveedores y control centralizado | Un único punto de falla, backups, hardening y mantenimiento a cargo del equipo | **Por evaluar** |
| C — Servicios administrados | Hosting web, API/PaaS, DB gestionada con pgvector, Redis gestionado y almacenamiento de objetos | Reducir operaciones manuales | Restricciones de planes, red privada y costo; compatibilidad debe verificarse | **Por evaluar** |

**Criterio de elección:** simplicidad para el equipo, costo total controlado, persistencia, seguridad, compatibilidad con pgvector, facilidad de demostrar HTTPS y posibilidad de desactivar los servicios al finalizar. No se afirma que alguna alternativa sea gratis, más barata o compatible sin validación actual de planes y límites.

## 6. Dependencias reales previas a una demo de autenticación

- **Restauración de sesión:** `POST /api/auth/refresh` devuelve solo `{accessToken}` y `restoreSession()` no recompone `SessionUser`; no declarar resuelto el flujo de recarga.
- **Registro:** no se detectó emisión/aceptación de invitaciones. Los PR internos #31/#32 llamados A-14/A-15 no implementaron esa funcionalidad; conservar la trazabilidad del plan original.
- **Modo web:** definir `NEXT_PUBLIC_REAL_AUTH` correctamente para la compilación/demo; la simulación no sustituye cuentas reales ni autorización del servidor.
- **Usuarios de prueba:** crear por mecanismo seguro acordado; no ejecutar seeds locales con cuentas ficticias inservibles como identidad productiva.
- **Pruebas:** E2E de autenticación pasaron localmente, pero aún no son un gate automático de CI; comprobar el flujo publicado en navegador y desde una red externa.
- **RAG:** alcance de demo con/sin asistente a acordar con Equipo C; no conectar credenciales o crear costos de IA por supuesto.
