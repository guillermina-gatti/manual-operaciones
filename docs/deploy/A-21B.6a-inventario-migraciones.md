# PispIAr — A-21B.6a · Inventario de migraciones Prisma y requisitos de pgvector

## Alcance y criterio de evidencia

Auditoría estática de las migraciones Prisma, los requisitos de PostgreSQL/pgvector y el empaquetado Docker existente, previa al diseño del flujo productivo de A-21B.6b. Se auditó el commit `fcfb520805b31ec2651a2b7c2b6257bb8f712b21` de `develop`, actualizado por avance rápido el 12 de noviembre de 2026, antes de crear la rama de trabajo.

No se conectó ninguna base, no se ejecutaron migraciones, seeds, resets ni `db push`, y no se validó infraestructura cloud. Por lo tanto:

- **Hecho observado:** surge directamente de archivos versionados en el commit auditado.
- **Inferencia:** consecuencia técnica razonable de esos archivos, pendiente de prueba controlada.
- **Supuesto no verificado:** depende del proveedor, la base o la operación productiva aún no definidos.

## Requisitos de PostgreSQL, pgvector y Prisma

### PostgreSQL y extensiones

**Hechos observados**

- El datasource Prisma usa `provider = "postgresql"`; el lock de migraciones también declara PostgreSQL.
- Desarrollo local y CI usan `pgvector/pgvector:pg16`. Esto prueba la intención de compatibilidad con PostgreSQL 16 en esos entornos, no la versión productiva.
- La migración 2 ejecuta `CREATE EXTENSION IF NOT EXISTS vector` y luego usa `vector(768)`, operador/clase `vector_cosine_ops` e índice HNSW.
- La migración 6 ejecuta `CREATE EXTENSION IF NOT EXISTS unaccent`, crea una configuración de texto y un índice funcional.
- El conjunto usa enums, UUID, arrays UUID, `TIMESTAMPTZ`, índices GIN/HNSW, índices únicos parciales, `CHECK`, una columna generada almacenada y `gen_random_uuid()`.
- El SQL no califica tablas/extensiones con schema. CI configura `?schema=public`; la URL productiva y su `search_path` no están verificados.

**Requisitos e inferencias a validar antes de producción**

- El servidor debe ofrecer una versión de pgvector compatible con HNSW y `vector_cosine_ops`, y debe tener disponibles los archivos de las extensiones `vector` y `unaccent`.
- El rol migrador necesita conectividad TLS según el proveedor y permisos DDL suficientes para extensiones, tipos, configuraciones de búsqueda, tablas, constraints e índices. El rol de runtime puede y debería tener permisos más acotados.
- Deben fijarse y comprobarse versión exacta de PostgreSQL y pgvector; el tag `pg16` hoy no fija una versión de pgvector por digest ni demuestra compatibilidad del proveedor elegido.
- Debe confirmarse el schema destino (esperado actualmente: `public`) y evitar que un `search_path` distinto instale objetos en otro schema.
- Antes de la primera aplicación debe conocerse si la base está vacía, ya tiene `_prisma_migrations` o contiene objetos/datos creados por otro mecanismo. Esa situación no puede inferirse del repositorio.

### Prisma y toolchain

| Elemento | Estado observado | Consecuencia para migraciones |
|---|---|---|
| Prisma CLI | `prisma` **7.10.0**, en `devDependencies` de la API | Está disponible tras una instalación completa; no queda en el deploy productivo actual. |
| Cliente Prisma | `@prisma/client` `^7.10.0`, resuelto a 7.10.0 en lock | El cliente generado se usa en runtime, pero no reemplaza al CLI. |
| Adaptador PostgreSQL | `@prisma/adapter-pg` `^7.10.1`, resuelto a 7.10.1 | Dependencia runtime; no instala el comando de migración. |
| Generación | `postinstall: prisma generate`; `build` vuelve a ejecutar `prisma generate` | El builder genera el cliente antes de compilar NestJS. `pnpm deploy --prod --ignore-scripts` evita regenerarlo en el paquete final. |
| Configuración | `apps/api/prisma.config.ts` apunta a `prisma/schema.prisma`, `prisma/migrations` y `DATABASE_URL` | `migrate deploy` necesita ejecutar desde el contexto correcto de la API y recibir esos archivos y la URL por secreto. |
| Seed | Configurado con `ts-node` para desarrollo | No forma parte de `migrate deploy` y no debe incorporarse al flujo productivo. |
| Plataforma | raíz: Node `>=24`, pnpm `12.11.2`; Docker: Node 24 Bookworm slim + OpenSSL | El artefacto migrador debería conservar versiones y librerías compatibles con el build. |
| SQL no modelable | `Unsupported("vector(768)")`, `Unsupported("tsvector")`, configuración FTS, HNSW y `CHECK` manuales | El historial SQL versionado es la fuente de aplicación; `db push` no es sustituto seguro. |

## Limitaciones del runtime Docker actual

La imagen final está correctamente reducida para ejecutar la API como usuario `node`, pero **no puede ejecutar `prisma migrate deploy` tal como está construida**:

1. `pnpm --filter api --prod deploy ... --ignore-scripts` conserva dependencias productivas; el CLI `prisma` está en `devDependencies`.
2. El stage `runtime` copia sólo `node_modules`, `dist` y `package.json` de la API.
3. No copia `prisma.config.ts`, `prisma/schema.prisma`, `prisma/migrations` ni `migration_lock.toml`.
4. pnpm se instala globalmente sólo en el builder, no en runtime.
5. El `CMD` inicia directamente `node dist/main.js`; no existe entrypoint, job ni gate de migración.

La CI comprueba que la imagen tenga la API compilada, el cliente generado, bcrypt y el adaptador PostgreSQL. No comprueba presencia ni ejecución del CLI de migraciones. El job E2E usa `prisma migrate reset --force` sobre una base local de test protegida por validaciones; ese mecanismo es destructivo y no es reutilizable en producción.

## Hallazgos

| ID | Prioridad | Tipo y evidencia | Impacto | Acción propuesta |
|---|---|---|---|---|
| MIG-01 | **P0** | **Hecho:** Docker runtime omite CLI, configuración, schema e historial de migraciones. | La imagen productiva actual no puede ejecutar `prisma migrate deploy`. | En A-21B.6b crear un artefacto/job migrador explícito a partir del mismo commit, sin agrandar innecesariamente el runtime de la API. |
| MIG-02 | **P0** | **Hecho:** Docker, Compose y CI no definen etapa productiva de migración; sólo existe reset E2E. | Un deploy puede iniciar la API contra un schema viejo o depender de una acción manual no auditable. | Diseñar un gate único, previo al rollout, que falle cerrado y registre commit/resultado sin exponer la URL. |
| MIG-03 | **P0** | **Supuesto no verificado:** no se eligieron/validaron PostgreSQL productivo, versión de pgvector, `unaccent` ni permisos del rol migrador. | La primera migración dependiente de una extensión puede fallar antes de crear el schema. | Validar matriz de compatibilidad y permisos con el proveedor; separar rol migrador de runtime cuando sea viable. |
| MIG-04 | **P0** | **Supuesto no verificado:** estado real, backup y `_prisma_migrations` de la base destino desconocidos. | Riesgo de drift, objetos preexistentes, historial incompatible o recuperación imposible. | Incorporar preflight de estado, backup/restauración y decisión de baseline antes de aplicar. |
| MIG-05 | **P1** | **Hecho + inferencia:** hay `CREATE INDEX` no concurrentes, `ALTER TABLE`, columna generada almacenada y un `UPDATE` de todos los pasos. | En una base con datos pueden producir locks, cómputo prolongado o timeout. El volumen real es desconocido. | Medir en staging con datos representativos; definir ventana, timeout, monitoreo y plan de continuación/forward-fix. |
| MIG-06 | **P1** | **Hecho:** pgvector, `tsvector`, HNSW, configuración FTS, parciales y `CHECK` manuales no están representados completamente por Prisma. | Regenerar o sincronizar con `db push` puede omitir o intentar alterar objetos críticos. | Tratar los SQL versionados como fuente de despliegue; agregar verificación post-migración de extensiones, índices y constraints. |
| MIG-07 | **P1** | **Hecho + riesgo:** desarrollo/CI usan el tag mutable `pgvector/pgvector:pg16`; no consta versión/digest de extensión. | Una reconstrucción futura podría probar contra otra combinación que producción. | Fijar la compatibilidad requerida y, en la implementación, fijar imagen/digest de validación cuando corresponda. |
| MIG-08 | **P1** | **Hecho + supuesto:** las migraciones usan nombres sin schema; sólo CI evidencia `schema=public`. | Un `search_path` o URL productiva distinta puede crear/buscar objetos en un schema inesperado. | Validar explícitamente URL, schema efectivo y ownership en el preflight, sin imprimir credenciales. |
| MIG-09 | **P1** | **Hecho:** Prisma no aporta migraciones descendentes en este historial y varias operaciones no son trivialmente reversibles. | “Rollback de aplicación” no revierte automáticamente DDL ni datos. | Definir restauración desde backup o forward-fix probado; no prometer rollback SQL automático. |
| MIG-10 | **P1** | **Hecho:** algunos índices únicos parciales advierten que fallan si existen duplicados; la migración 14 modifica datos existentes. | Una base con drift o datos incompatibles puede detener el deploy. | Agregar consultas de preflight de sólo lectura y ensayo sobre snapshot sanitizado/representativo. |
| MIG-11 | **P2** | **Hecho:** existen referencias lógicas por UUID sin FK entre módulos/equipos. | No bloquea `migrate deploy`, pero limita verificaciones de integridad y condiciona el orden funcional. | Mantenerlo fuera de A-21B.6b salvo que el equipo dueño acuerde cambios de schema; documentar en verificaciones. |

## Estrategias posibles para A-21B.6b

| Estrategia | Ventajas | Costos/riesgos | Evaluación |
|---|---|---|---|
| **Imagen/target migrador dedicado + job de una sola ejecución** | Mismo código y lock que el release; incluye sólo lo necesario; desacopla privilegios y ciclo de vida de la API; auditable. | Requiere nuevo target Docker, comando, orquestación, secreto y gate de rollout. | **Recomendada** para diseñar en A-21B.6b. Ejecutar una sola instancia por release. |
| Runner de CI/CD con checkout e instalación completa | Cambio inicial simple; el CLI y archivos ya existen en el workspace. | Depende de red/instalación al desplegar, aumenta superficie del runner y exige acceso seguro a DB; no hay CD actual. | Alternativa válida si la plataforma ofrece runner privado y artefactos reproducibles. |
| Migrar en el entrypoint de cada API | Automatiza el arranque. | Acopla disponibilidad a DDL, multiplica intentos concurrentes y exige privilegios de migrador en cada réplica; la imagen actual tampoco lo soporta. | **No recomendada** como diseño productivo por defecto. |
| Aplicar SQL manualmente desde consola del proveedor | Puede destrabar una emergencia controlada. | Fácil perder trazabilidad/orden y desalinear `_prisma_migrations`; depende de intervención humana privilegiada. | Sólo contingencia con runbook y reconciliación explícita, no flujo normal. |

Ninguna estrategia debe ejecutar `migrate dev`, `migrate reset`, seeds ni `db push` en producción. La decisión final también depende de la plataforma de despliegue y conectividad privada todavía no verificadas.

## Próximos pasos

### A-21B.6b — Diseño e implementación mínima

- Elegir el mecanismo de job único y documentar su límite de confianza.
- Empaquetar CLI + `prisma.config.ts` + schema + historial desde el mismo commit/lock del release.
- Definir preflight no destructivo, inyección segura de `DATABASE_URL`, exclusión de seed/reset y gate previo al rollout.
- La implementación local de A-21B.6b y las pruebas aisladas de A-21B.6c pueden avanzar sin infraestructura cloud.
- MIG-03 y MIG-04 bloquean la ejecución sobre la base productiva y el rollout hasta contar con responsables, compatibilidad verificada, estado previo conocido y respaldo recuperable.

### A-21B.6c — Ensayo controlado

- Probar el artefacto primero sobre una base efímera vacía compatible y luego sobre un snapshot sanitizado o dataset representativo.
- Registrar tiempos, locks, estado de `_prisma_migrations` y presencia de extensiones/índices/constraints, sin volcar credenciales ni datos sensibles.
- Ensayar fallo, reintento seguro y recuperación/forward-fix.

### A-21B.6d — Runbook y habilitación productiva

- Definir aprobaciones, responsable operativo, backup restaurable, ventana, monitoreo y criterio de abortar.
- Ejecutar una sola vez antes del rollout de API y conservar evidencia de commit, migraciones aplicadas y verificaciones posteriores.
- Mantener separado el rol migrador del runtime y retirar acceso elevado al finalizar, si el proveedor lo permite.
