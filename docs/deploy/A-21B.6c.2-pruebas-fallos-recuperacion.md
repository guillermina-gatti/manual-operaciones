# PispIAr — A-21B.6c.2 · Pruebas aisladas de fallos y recuperación

## Alcance

Esta tarea extiende el smoke test de A-21B.6c.1 para validar un fallo controlado de conexión, cleanup ante ese fallo, protección por ownership, reintento sobre un ambiente nuevo e idempotencia reforzada del historial Prisma.

La prueba se ejecutó el 12 de noviembre de 2026 desde `develop` actualizado con PR #74. No se modificaron `schema.prisma`, las 16 migraciones SQL, Docker Compose, el runtime API ni código de aplicación.

## Modos del script

[`scripts/deploy/test-prisma-migrations.ps1`](../../scripts/deploy/test-prisma-migrations.ps1) conserva `Success` como modo por defecto y agrega:

| Modo | Comportamiento |
|---|---|
| `ConnectionFailure` | Crea PostgreSQL/red/imagen nuevos, verifica ownership con un canary, ejecuta el migrador con contraseña inválida, exige un error de autenticación y limpia todo. |
| `RecoverySuccess` | Ejecuta el flujo exitoso existente sobre recursos nuevos y compara el historial Prisma completo antes/después del segundo deploy. |
| `FailureRecovery` | Orquesta primero `ConnectionFailure` y, sólo si pasa sus aserciones y cleanup, inicia `RecoverySuccess` en otro ambiente aislado. |

Comando ejecutado:

```powershell
pwsh -NoProfile -File scripts/deploy/test-prisma-migrations.ps1 -Mode FailureRecovery
```

## Garantías de aislamiento

- Docker Desktop local con contexto obligatorio `desktop-linux` y engine Linux.
- Un identificador aleatorio distinto por subescenario.
- PostgreSQL `pgvector/pgvector:pg16` nuevo, base/rol/contraseña aleatorios y almacenamiento `tmpfs`.
- Red dedicada `--internal`, sin puertos publicados ni volumes.
- Preflight de base vacía, ownership temporal y ausencia de `_prisma_migrations`.
- Credenciales pasadas en memoria; no se imprimen contraseñas ni conexiones completas.
- Cleanup en `finally`, limitado por nombre exacto y label `io.pispiar.run` exacto.
- Verificación posterior dentro del script y comprobación independiente por `io.pispiar.task=A-21B.6c.2`.

## Escenarios y resultados observados

### 1. Fallo de conexión controlado

Se inició el migrador en la red interna correcta, pero con una contraseña aleatoria distinta de la creada para PostgreSQL. El resultado esperado era que `prisma migrate deploy` terminara con un error de autenticación reconocido, sin crear `_prisma_migrations`.

Resultado sanitizado:

```text
RESULTADO=FALLO_CONTROLADO_OK
CONNECTION_FAILURE=EXPECTED
DURACION_TOTAL_MS=13167
LIMPIEZA=OK
```

El script distingue el fallo esperado mediante la firma de error de autenticación de Prisma/PostgreSQL. Cualquier éxito inesperado u otro tipo de error hace fallar el escenario.

### 2. Seguridad de ownership

Se creó una red canary propia de la prueba con un marker de corrida deliberadamente distinto. El helper real de cleanup recibió el marker de la corrida principal y rechazó eliminarla. Se verificó que la red siguiera existiendo; recién después fue eliminada usando su marker exacto.

Resultado sanitizado:

```text
OWNERSHIP_SAFETY=OK
```

Esto prueba que coincidir por nombre o task label no alcanza para borrar un recurso: también debe coincidir el identificador único de ownership.

### 3. Cleanup después del fallo

Después del rechazo de autenticación, `finally` eliminó el contenedor PostgreSQL, el contenedor fallido si todavía existía, la red interna y la imagen construida. Cada eliminación validó primero su marker.

El script informó `LIMPIEZA=OK`. La comprobación independiente posterior encontró:

- 0 contenedores remanentes;
- 0 redes remanentes;
- 0 imágenes remanentes.

### 4. Reintento en ambiente nuevo

El orquestador lanzó otro proceso PowerShell, generando nuevos nombres, red, credenciales, base, contenedor e imagen. No se reutilizó el PostgreSQL del fallo.

Resultado:

| Verificación | Evidencia |
|---|---|
| Migraciones | 16 aplicadas correctamente |
| Extensiones | `vector` y `unaccent` presentes |
| FTS e índices | `es_unaccent`, HNSW y GIN verificados |
| Primera ejecución | 1483 ms |
| Segundo deploy | 1422 ms; sin migraciones nuevas |
| Duración total del retry | 14404 ms, incluida limpieza |
| Cleanup | OK |

La suite finalizó con `RETRY=OK` y `FAILURE_RECOVERY=OK`.

## Comparación reforzada del historial

Antes y después del segundo `migrate deploy`, el script obtiene para cada fila de `_prisma_migrations`:

- `migration_name`;
- `checksum`;
- si `finished_at` está informado;
- si `rolled_back_at` permanece nulo;
- `applied_steps_count`.

Las listas ordenadas deben coincidir byte por byte. Además, el test rechaza checksums vacíos, pasos aplicados no positivos, migraciones sin finalizar o marcadas como rollback.

Resultado:

```text
IDEMPOTENCIA=OK
HISTORIAL_IDEMPOTENTE=NOMBRES+CHECKSUMS+ESTADO OK
```

## Resultado consolidado

```text
CONNECTION_FAILURE=EXPECTED
OWNERSHIP_SAFETY=OK
LIMPIEZA=OK
RETRY=OK
HISTORIAL_IDEMPOTENTE=NOMBRES+CHECKSUMS+ESTADO OK
FAILURE_RECOVERY=OK
```

No se ejecutaron `migrate reset`, `migrate dev`, `db push`, seeds, `prisma migrate resolve`, Docker prune ni operaciones cloud.

## Limitaciones conocidas

- No se inyectó una falla a mitad de un archivo SQL. Hacerlo requeriría alterar una migración versionada, introducir un historial artificial o usar `migrate resolve`; esas opciones quedarían fuera del alcance seguro de esta tarea.
- Por lo anterior, no se validó recuperación de una migración parcialmente aplicada. En producción debe resolverse mediante backup restaurable, análisis del estado real y forward-fix/runbook aprobado; no mediante automatismos ensayados sólo sobre datos descartables.
- Las bases estaban vacías. No se midieron locks, reescrituras o tiempos con volumen representativo.
- No se validaron proveedor cloud, TLS, conectividad privada, separación final de roles, backup/restauración ni versión/digest productivo de pgvector.
- Los tiempos locales con build cacheado no son un benchmark productivo.

## Checklist de aceptación

- [x] Fallo de autenticación intencional y determinista ejecutado.
- [x] Fallo esperado distinguido de errores inesperados.
- [x] Base intacta y sin `_prisma_migrations` después del fallo de conexión.
- [x] Cleanup posterior al fallo verificado.
- [x] Rechazo de eliminación con marker de ownership incorrecto comprobado.
- [x] Retry sobre ambiente completamente nuevo exitoso.
- [x] Historial comparado por nombres, checksums y estado antes/después del segundo deploy.
- [x] Cero recursos Docker remanentes confirmados.
- [x] Sin cambios a schema, migraciones SQL, Compose o aplicación.
