# PispIAr — A-21B.6b · Imagen dedicada para migraciones Prisma

## Propósito

Esta tarea agrega una imagen Docker one-off para ejecutar migraciones Prisma de manera separada del runtime NestJS. La imagen queda vinculada al mismo `pnpm-lock.yaml`, schema e historial SQL que el release, pero no ejecuta migraciones durante el build ni al iniciar la API.

El alcance de A-21B.6b es exclusivamente empaquetado y verificación estática. **No se conectó ninguna base ni se ejecutó `prisma migrate deploy`**. La ejecución real sobre PostgreSQL local descartable corresponde a A-21B.6c.

## Arquitectura

El `apps/api/Dockerfile` conserva `runtime` como último target y mantiene sin cambios sus instrucciones de ejecución. Agrega dos targets independientes:

1. `migrator-builder`: usa Node 24 Bookworm slim, OpenSSL, CA y pnpm 12.11.2; instala desde el lock únicamente el workspace `prisma-migrator` y genera un deploy productivo autocontenido.
2. `migrator`: usa Node 24 Bookworm slim, OpenSSL y CA; copia las dependencias productivas del CLI, la configuración Prisma, el schema y las 16 migraciones SQL.

El paquete `apps/migrator/package.json` fija exactamente `prisma` 7.10.0 y `dotenv` 18.0.8. No agrega versiones nuevas al lock: declara como dependencias directas versiones ya resueltas por el proyecto.

### Contrato de ejecución

| Propiedad | Valor |
|---|---|
| Build target | `migrator` |
| Usuario | `node` |
| Working directory | `/app` |
| Entrypoint | `./node_modules/.bin/prisma` |
| Comando por defecto | `--help` |
| Variable secreta requerida para migrar | `DATABASE_URL` |
| Red durante verificaciones estáticas | `none` |

El comando por defecto sólo muestra ayuda. Por diseño, aplicar migraciones exige pasar explícitamente los argumentos `migrate deploy`; iniciar la imagen sin argumentos no consulta una base.

## Contenido requerido de la imagen

| Ruta | Uso |
|---|---|
| `/app/node_modules/.bin/prisma` | CLI Prisma 7.10.0. |
| `/app/node_modules/@prisma` y dependencias transitivas | Schema engine Linux/OpenSSL y runtime del CLI fijados por el lock. |
| `/app/prisma.config.ts` | Configuración Prisma 7; toma `DATABASE_URL` del entorno en runtime. |
| `/app/prisma/schema.prisma` | Schema PostgreSQL auditado. |
| `/app/prisma/migrations/migration_lock.toml` | Provider del historial de migraciones. |
| `/app/prisma/migrations/*/migration.sql` | Las 16 migraciones versionadas de A-21B.6a. |

La imagen no copia `.env`, `prisma/seed.ts`, `test/`, fixtures, fuentes NestJS ni el artefacto compilado de la API. Tampoco declara `DATABASE_URL` en Dockerfile: debe inyectarse sólo al crear el job autorizado.

## Construcción

Ejecutar desde la raíz del repositorio:

```powershell
docker build --progress=plain --target migrator -f apps/api/Dockerfile -t pispiar-migrator:local .
```

El build puede acceder al registro de paquetes y al registry de la imagen base. Todas las dependencias JavaScript quedan resueltas por `pnpm-lock.yaml`; no se usa `npx` ni se selecciona una versión flotante del CLI.

## Verificación estática segura

Estas verificaciones no reciben `DATABASE_URL` y los contenedores se ejecutan sin red:

```powershell
docker image inspect pispiar-migrator:local --format "user={{.Config.User}} entrypoint={{json .Config.Entrypoint}} cmd={{json .Config.Cmd}} workdir={{.Config.WorkingDir}}"
docker run --rm --network none pispiar-migrator:local --version
docker run --rm --network none pispiar-migrator:local --help
```

El workflow `.github/workflows/ci.yml` además comprueba que:

- el usuario sea `node`, el working directory sea `/app`, el entrypoint sea el CLI y el comando por defecto sea `--help`;
- estén presentes config, schema, lock de migraciones y los 16 `migration.sql`;
- Prisma sea exactamente 7.10.0;
- no estén presentes `.env`, seed ni directorio de tests;
- `prisma --version` funcione con `--network none`, evitando descargas implícitas durante la verificación.

## Comando one-off de migración

> **NO EJECUTADO EN A-21B.6b.** Reservado para A-21B.6c sobre una base local nueva y descartable, y para producción sólo después de cumplir todos los prerrequisitos.

La variable `DATABASE_URL` debe existir previamente en el entorno protegido del operador o ser inyectada por el secret manager del job. No debe escribirse su valor en la línea de comandos, logs, documentación ni manifiestos versionados.

```powershell
docker run --rm --env DATABASE_URL pispiar-migrator:RELEASE_TAG migrate deploy
```

Debe ejecutarse como un único job previo al rollout de la API, nunca como parte del `ENTRYPOINT` de cada réplica ni durante `docker build`. No usar `migrate dev`, `migrate reset`, `db push` o seeds en producción.

## Limitaciones y prerrequisitos productivos

- A-21B.6b prueba empaquetado, metadatos y CLI sin red; no prueba conectividad, permisos ni aplicación del SQL.
- El PostgreSQL destino debe ser compatible con el baseline PostgreSQL 16 y ofrecer pgvector con HNSW, `vector_cosine_ops` y la extensión `unaccent`.
- El rol migrador necesita permisos DDL y de creación de extensiones/configuraciones de texto. El rol normal de la API debería permanecer separado y con privilegios menores.
- Deben confirmarse TLS, schema/search path esperado (`public` actualmente), estado de `_prisma_migrations`, ausencia o tratamiento de drift y compatibilidad de datos con índices únicos.
- Antes de producción se necesita backup restaurable, responsable, ventana, monitoreo, criterio de abortar y estrategia de recuperación/forward-fix.
- Los `CREATE INDEX` no concurrentes, `ALTER TABLE`, columna generada y actualización de pasos identificados en A-21B.6a pueden tomar locks; su duración debe medirse con datos representativos.
- El tag de la base `pgvector/pgvector:pg16` usado en desarrollo/CI no fija por sí solo la versión productiva de pgvector.
- La imagen contiene dependencias transitivas propias del paquete oficial Prisma CLI; no contiene dependencias de runtime de NestJS ni de la web.
