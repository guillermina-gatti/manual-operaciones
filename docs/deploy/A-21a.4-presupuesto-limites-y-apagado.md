## 1. Objetivo y límites

Preparar un marco de decisión para estimar los costos reales de una demo pública, limitar gastos imprevistos y desactivar recursos al terminar. Esta microtarea **no despliega, configura, contrata ni modifica** AWS, Vercel, Supabase, Redis, S3, dominios ni otros proveedores.

Sin topología aprobada, país/región, titular de cuenta y presupuesto acordado, **no es correcto asignar un costo mensual definitivo, prometer gratuidad ni afirmar un saldo de crédito disponible**. Se documentan rubros y cómo obtener evidencias de precios antes de aprobar A-21b.

## 3. Rubros que deben cotizarse (sin inventar precios)

| Rubro | Dependencia/caso de uso | Variables de costo a verificar | Pregunta clave |
|---|---|---|---|
| Frontend Next.js | Hosting web y proxy `/api` | Plan, límites de build, transferencia y solicitudes | ¿El plan admite uso y transferencia necesarios? |
| API NestJS | Proceso HTTP con HTTPS y reinicio | Horas de cómputo, RAM/CPU, almacenamiento, tráfico y snapshots | ¿Puede mantener la API activa durante la demo? |
| PostgreSQL + pgvector | Datos, sesiones, búsquedas | Instancia, GB almacenados, backups, egress, compatibilidad `vector` | ¿Incluye pgvector y restauración comprobable? |
| Redis | Rate limiting y servicios que lo consumen | Memoria, conexiones, tráfico, persistencia o servicio privado | ¿Puede quedar privado y estable? |
| S3 o compatible | Archivos/documentos persistentes | Almacenamiento, operaciones, salida de datos, transferencias | ¿Soporta el adaptador actual y permisos mínimos? |
| DNS y certificados | URLs HTTPS | Dominio/renovación si aplica, DNS y servicios adicionales | ¿Podemos usar dominio existente autorizado? |
| Observabilidad y backup | Operación, recuperación | Logs, retención, métricas, almacenamiento de backups | ¿Qué plan de recuperación resulta viable? |
| IA / Gemini u otro proveedor | **Solo si** la demo incluye RAG | Solicitudes, tokens, cuotas, almacenamiento/embeddings, límites | ¿Equipo C confirma necesidad y proveedor activo? |
| Tráfico entre proveedores | Web → API → DB / objetos | Egress entre regiones/cuentas, transferencias y tasas extra | ¿La topología multiproveedor eleva el costo? |

**Cómo estimar:** para cada servicio registrar URL oficial de su calculadora/precios, fecha de consulta, plan/región elegidos, unidad de facturación, supuestos de carga, límite gratuito aplicable (si se verificó), impuestos y riesgo de excedentes. Repetir antes de contratar: los precios y las condiciones cambian.

## 5. Límites, alertas y medidas preventivas

1. **Antes de crear recursos:** acordar titular, presupuesto, permiso de gasto y fecha/condición de baja por escrito; revisar qué alertas de facturación ofrece cada proveedor.
2. **Alertas de consumo:** configurar umbrales **a definir** (aviso temprano, aviso crítico y actuación). **Una alerta no equivale a un bloqueo del gasto**; comprobar si el servicio admite cuota dura o suspensión automática segura.
3. **Cuotas técnicas:** limitar tamaños de instancias, almacenamiento, backups, retención de logs, llamadas IA, operaciones de objetos y tráfico cuando el servicio lo permita; vigilar componentes de cobro por consumo.
4. **Accesos:** MFA, usuarios individuales, mínimo privilegio, secretos fuera del repo y sin claves personales compartidas. Preferir credenciales temporales/roles.
5. **Revisión periódica:** durante la demo, el responsable inspecciona panel de costos y uso; anota fecha y desvíos sin compartir identificadores financieros ni capturas sensibles.
6. **Ante costo no esperado:** detener nuevas cargas/operaciones, evaluar suspensión del servicio con el responsable, registrar causa y autorización; no borrar bases ni documentos de terceros improvisadamente.
7. **Separación de entornos:** nunca ejecutar E2E destructivos contra bases cloud. `prisma migrate reset` queda restringido a bases **locales de prueba** conforme al arnés del proyecto.

## 6. Primera demo mínima: propuesta condicionada

**Criterio de reducción de riesgo:** acordar con B/C qué flujo mínimo debe demostrarse para cumplir la consigna antes de activar IA o recursos adicionales. Una secuencia candidata es web HTTPS → login real → consulta autorizada de documentos/procedimientos → logout, con datos ficticios persistentes.

Esta propuesta **no significa que ese flujo ya funcione completo en producción**: `restoreSession()` todavía no reconstruye sesión tras recargar y el registro por invitación no se detectó implementado. Tampoco equivale a declarar RAG fuera del MVP: esa decisión requiere aval del equipo/docente.

La API en `NODE_ENV=production` exige `S3_BUCKET`, por lo que **no se puede asumir** que una primera instancia productiva levantará sin almacenamiento persistente configurado. Redis también es una dependencia efectiva para controles de autenticación. Cualquier fase reducida debe respetar seguridad y dependencias reales.

## 7. Apagado, conservación y eliminación segura

**Disparador:** fecha de fin de pruebas/defensa o decisión expresa del equipo. El momento exacto está **pendiente**, sin fecha inventada.

| Orden | Acción propuesta | Precaución/evidencia |
|---|---|---|
| 1 | Confirmar que ya no habrá demo/uso y obtener aprobación del responsable | Acuerdo registrado y aviso al equipo |
| 2 | Detener altas y tráfico/operaciones, deshabilitar integraciones y tareas programadas | Evitar consumos durante la baja |
| 3 | Identificar datos a conservar o eliminar y su finalidad | Solo datos ficticios si es demo; respetar políticas de retención |
| 4 | Realizar export/backup autorizado **si es necesario**, confirmar restaurabilidad y ubicación segura | Nunca subir dumps ni credenciales a GitHub |
| 5 | Desactivar o eliminar recursos en orden seguro: web/API, trabajos, Redis, DB, objetos, backups/snapshots, discos e IPs según dependencia | Detener una VM no necesariamente detiene cobros de discos/IPs/backups |
| 6 | Revocar credenciales, roles y tokens de proveedor; revisar dominios y certificados | Verificar ausencia de accesos residuales |
| 7 | Consultar facturación después de la baja y confirmar ausencia de recursos activos y cargos pendientes | Captura sanitizada, fecha y responsable; atención a cargos retrasados |

**No eliminar servicios ni datos** hasta tener autorización, responsable y criterio de conservación. La infraestructura puede vivir fuera de este repo; la ausencia de archivos Terraform/Docker de deploy no prueba que no exista.

## 8. Matriz de riesgos y mitigaciones

| Riesgo | Impacto | Mitigación previa |
|---|---|---|
| Servicio gratuito excede límites o pasa a pago | Cargo inesperado | Confirmar condiciones actuales, alertas y tope aprobado |
| VM detenida aún factura almacenamiento/IP/snapshots | Costo después de defensa | Checklist de eliminación y control de factura final |
| Transferencias entre proveedores o regiones | Egress no previsto | Cotizar flujo completo, ubicar servicios de forma razonable |
| Falta de dueño de cuenta o de MFA | Pérdida de acceso / incidentes | Dueño y suplente, accesos individuales |
| Redis/DB expuestos públicamente | Incidente de seguridad | Red privada, firewall y verificación externa |
| Archivos guardados en RAM en producción | Pérdida de datos | S3/compatible privado y persistente obligatorio |
| Activar IA sin cuotas | Consumo variable elevado | Alcance definido con C, límites y monitoreo |
| Baja sin retención acordada | Pérdida de evidencia | Checklist de backup/expurgo acordado |
