## 3. Arquitectura mínima a evaluar (NO aprobada)

```text
Navegador HTTPS
    |
    v
Frontend Next.js (hosting y URL por acordar)
    |  fetch('/api/...') / rewrite con API_URL
    v
API NestJS HTTPS (hosting y DNS por acordar)
    |-- PostgreSQL con pgvector (acceso privado / TLS según proveedor)
    |-- Redis privado (rate limiting)
    `-- Almacenamiento de objetos S3 o compatible (persistencia de documentos)
```

El plan v2.1 propone, **como alternativa para evaluar**, Vercel + EC2 HTTPS + PostgreSQL Supabase, con Redis y S3 según necesidades. Ningún proveedor se considera elegido hasta ratificación del equipo. La API tiene dependencia de almacenamiento persistente para carga de documentos en modo producción: `StorageModule` rechaza `NODE_ENV=production` sin `S3_BUCKET`.

## 5. Dependencias y riesgos antes de desplegar

1. **Registro por invitación**: plan v2.1 lo considera necesario para R2; no avanzar suponiendo que `A-14`/`A-15` de los PR #31–32 lo implementaron. Esos PR fueron, respectivamente, documentación y tests E2E. Mantener un ticket distintivo para invitaciones y enlazarlo al plan original.
2. **Sesión al recargar**: `AuthController.refresh` devuelve únicamente `accessToken`; `restoreSession()` en la web no reconstruye `SessionUser`. Validar contrato y comportamiento antes de defender persistencia de sesión.
3. **CI no es E2E**: la suite A-15 pasó localmente, pero el workflow no la ejecuta. El plan v2.1 prevé A-20a (Vitest web) y A-20b (E2E PostgreSQL/Redis aislados en Actions).
4. **HTTP y cookies**: verificar `Secure`, `SameSite`, `Path`, proxy y dominios reales de manera end-to-end. No inferir éxito productivo por pruebas locales.
5. **Persistencia**: el modo en memoria no es aceptable para documentos en producción; provisionar almacenamiento persistente seguro antes de activar cargas reales.
6. **Prisma/pgvector**: revisar migraciones e índices especiales de `chunks` antes de aplicar en cloud; prohibir `prisma migrate reset` fuera de bases locales de tests.
7. **Costos**: no iniciar instancias EC2, RDS, Supabase, bucket ni recursos facturables sin responsables y límites acordados.
