## 1. Propósito, alcance y reglas

Identificar las variables y las conexiones que el código utiliza, distinguir configuración pública y secretos, y establecer controles verificables para un eventual despliegue con HTTPS. La selección de proveedores, red, presupuesto, región, cuentas y responsables sigue **pendiente de acuerdo del equipo** (A-21a.1/A-21a.2).

**Solo documentación:** no se crean recursos, credenciales, entornos ni cuentas; no se modifican `.env`, Docker, CI, API ni web. Se documentan **nombres** de variables, nunca valores reales. No asumir que el contenido de `.env.example` es un inventario exhaustivo del código, ni que las variables declaradas allí tienen integración funcional.

## 3. Gestión de secretos: propuesta de política

1. Un entorno por servicio y propósito: desarrollo, pruebas locales, staging (si existe) y producción. No reutilizar claves JWT ni contraseñas de DB entre ambientes.
2. Guardar `DATABASE_URL`, `JWT_SECRET`, credenciales Redis/AWS y claves IA en un gestor de secretos o configuración protegida del proveedor; permisos mínimos y acceso solo para quienes operan cada servicio.
3. Nunca poner secretos en `NEXT_PUBLIC_*`, URLs visibles, variables de compilación pública, código cliente, commits, issues, PR, logs, capturas, artefactos, imágenes Docker ni documentación.
4. Preferir identidad/rol del runtime para S3 frente a claves AWS permanentes. El SDK actual permite obtener credenciales desde su cadena estándar; confirmar la identidad realmente utilizada en cloud.
5. No publicar `.env` reales. `.gitignore` excluye `.env` y `.env.*` salvo `.env.example`, pero eso no sustituye una revisión antes de hacer commit. Los ejemplos deben contener campos vacíos o datos ficticios.
6. Registrar **responsable**, almacenamiento, rotación y revocación de cada secreto en una tabla privada de operación. En el repositorio solo se registran nombres, requisitos y existencia de controles; nunca valores.
7. Si se sospecha filtración, revocar y rotar el secreto desde el proveedor, revisar accesos/impacto y auditar historial/logs. Borrar una línea de Git **no** revoca una credencial comprometida.
8. No copiar el `.env` local de una desarrolladora (PostgreSQL `localhost:5433`) a ningún servidor; su cambio local de `docker-compose.yml` permanece fuera de la rama y de los PR.

## 4. Matriz de puertos y fronteras de red

| Conexión | Protocolo / puerto de referencia | Exposición prevista | Requisito de seguridad | Estado |
|---|---|---|---|---|
| Navegador → hosting web | HTTPS TCP `443` | Pública | TLS válido, dominio confirmado; HTTP `80` solo si redirige o se usa para certificados | **Por verificar** |
| Web Next.js → API NestJS | HTTPS TCP `443` hacia destino de `API_URL` | Tránsito servidor-servidor; URL de API puede ser pública si el hosting lo exige | TLS válido, URL HTTPS, límites de acceso, logs sin tokens | **Por decidir** |
| Reverse proxy → proceso NestJS | HTTP TCP `3000` por defecto, o `PORT` definido | **Interna**, no exponer directamente | Permitir solo proxy/localhost/red privada; revisar cabeceras `X-Forwarded-*` y proxies confiables | **Por implementar/verificar** |
| API → PostgreSQL + pgvector | TCP `5432` como valor habitual; puerto real del proveedor por decidir | **Privada** | Solo API/migraciones; TLS, permisos mínimos, backups; no abrir 0.0.0.0/0 a DB | **Por decidir** |
| API → Redis | TCP `6379` como valor habitual; puerto real por decidir | **Privada** | Sin acceso público; ACL/contraseña/TLS si aplica, red restringida; revisar rate limit | **Por decidir** |
| API → S3/compatible | HTTPS TCP `443` | Salida a proveedor de objetos | Bucket privado; identidad mínima y URLs firmadas; comprobar CORS si el browser descarga directo | **Por decidir** |
| API → proveedor de IA | HTTPS TCP `443` si se habilita | Salida controlada | Solo con alcance de IA acordado; cuotas, autorización de fragmentos y secretos | **Condicional** |
| Operación → servidor | Acceso administrativo a definir (SSH/gestor de sesiones) | **Restringida**, no pública indiscriminada | MFA, identidades individuales, política de rotación y registro | **Por decidir** |

**Hecho local vs. producción:** el `docker-compose.yml` versionado publica PostgreSQL `5432:5432` y Redis `6379:6379` en desarrollo; la configuración personal de pruebas usa PostgreSQL en `127.0.0.1:5433`. Estos puertos **no autorizan** exposición pública de DB o Redis en producción. La topología final puede cambiar puertos y proveedores.

## 5. HTTPS, cookies, proxy e IP real

### Confirmado por lectura de código

- `apps/web/next.config.ts` reescribe `fetch('/api/...')` mediante la URL de servidor `API_URL` y conserva el límite de proxy de `11mb` para cargas de hasta 10 MB.
- `AuthController` configura la cookie `refreshToken` con `httpOnly`, `sameSite: 'lax'`, `path: '/api/auth'` y `secure: true` cuando `NODE_ENV === 'production'`.
- `apps/api/src/main.ts` inicia Nest en `PORT ?? 3000`; no se observó configuración explícita de `trust proxy` en `main.ts` ni en `app.setup.ts` revisados.
- El controlador de autenticación toma `req.ip` como parte de los metadatos de sesión/limitación. Detrás de un proxy hace falta verificar que refleje la IP correcta **sin confiar en cabeceras de cualquier cliente**.
- Swagger se publica desde `app.setup.ts` en `/api/docs` sin una protección propia documentada en ese archivo; revisar exposición en producción.

### Pruebas de aceptación obligatorias antes de A-21c/A-22

1. Desde un navegador externo verificar certificado, dominio, redirección HTTP → HTTPS y ausencia de mixed content.
2. Confirmar que Next puede acceder al `API_URL` real por HTTPS; que no usa localhost, HTTP ni secretos embebidos en la URL.
3. Comprobar login y refresh en navegador: cookie `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/api/auth`; no exponer refresh token en JSON, localStorage o logs.
4. Validar logout, expiración, permisos `401/403/404` y sesión tras recarga **cuando la restauración esté implementada**; hoy no lo está.
5. Evaluar el modelo de riesgo CSRF para operaciones basadas en cookie. `SameSite=Lax` ayuda, pero no debe tratarse como prueba completa de protección CSRF.
6. Configurar y probar una cadena de proxies confiables antes de habilitar `trust proxy`; verificar rate limiting con IP real y evitar que una cabecera falsificada permita saltar límites.
7. Decidir si `/api/docs` debe restringirse, deshabilitarse o exponerse con acceso controlado en producción; comprobar decisión de forma externa.
8. Revisar seguridad de cabeceras y CORS **solo según topología elegida**; el rewrite mismo origen evita exigir CORS para la petición del navegador a Next, pero no resuelve todos los escenarios de descarga S3.
9. Probar subida de archivo hasta 10 MB y descarga autorizada (URLs firmadas), conservando el límite de Next de 11 MB y sin publicar el bucket.
10. Si hay IPs o certificados diferentes para staging y producción, aislar DNS, almacenamiento, base y secretos para impedir contaminación cruzada.
