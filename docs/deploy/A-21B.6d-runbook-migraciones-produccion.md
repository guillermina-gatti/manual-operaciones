# PispIAr — A-21B.6d · Runbook de migraciones Prisma en producción

## 1. Alcance, evidencia y responsabilidades

Este runbook prepara una futura ejecución productiva de `prisma migrate deploy`. Es documentación operativa: no habilita por sí sola un despliegue, no reemplaza la aprobación del cambio y no confirma la infraestructura de AWS.

### Evidencia disponible

| Estado | Evidencia y límite |
|---|---|
| Verificado localmente | La imagen dedicada `migrator`, construida desde el mismo repositorio que la API, aplicó las 16 migraciones existentes al cierre de PR #75 sobre PostgreSQL 16 + `pgvector/pgvector:pg16`, en una base nueva, aislada y descartable. Una segunda ejecución no produjo cambios. |
| Verificado localmente | `_prisma_migrations` conservó nombres, checksums y estado; quedaron presentes `vector`, `unaccent`, `public.es_unaccent`, los índices HNSW/GIN y constraints críticos. Un fallo de autenticación previo al DDL no creó `_prisma_migrations`; el retry exitoso se hizo sobre un ambiente nuevo. |
| No verificado | Proveedor y topología AWS, versión exacta de PostgreSQL/pgvector, digest de la imagen de base, TLS, red privada, credenciales, permisos mínimos, identidad de la base, datos y drift reales, duración/locks con volumen productivo, backup/restauración y orquestador de despliegue. |
| No verificado | Recuperación de una migración parcialmente aplicada. No se inyectó un fallo a mitad de un SQL ni se probó `prisma migrate resolve`. Los tiempos locales sobre base vacía no son una ventana productiva. |

### Roles

| Rol | Responsabilidad |
|---|---|
| Responsable de release | Fija el SHA, aprueba artefactos y ventana, coordina el GO/NO-GO y autoriza el rollout de API. |
| Operador/a de plataforma | Ejecuta preflight y el único job migrador, registra evidencia sanitizada y detiene el flujo ante cualquier desvío. |
| Responsable de base de datos | Confirma identidad, compatibilidad, estado, privilegios, locks, drift y estrategia de recuperación; dirige restauraciones o forward-fixes. |
| Responsable de seguridad | Valida acceso temporal, mínimo privilegio, inyección/rotación de secretos, TLS y ausencia de datos sensibles en evidencia. |
| Responsable de aplicación | Valida compatibilidad del SHA de API con el schema migrado y realiza smoke tests funcionales. |
| Responsable de continuidad | Acredita backup, retención, prueba de restauración, RPO/RTO acordados y capacidad disponible durante la ventana. |

Una misma persona puede cubrir más de un rol sólo si el equipo lo aprueba; las decisiones y evidencias se registran por rol, no por nombre en este documento.

## 2. Preflight y decisión GO / NO-GO

Completar el checklist en el registro privado del cambio. Cualquier casillero obligatorio sin evidencia implica **NO-GO**.

### Release y artefacto

- [ ] Cambio aprobado, ticket/registro operativo abierto, ventana y canal de coordinación confirmados.
- [ ] SHA completo e inmutable de release registrado; corresponde al código y al historial `apps/api/prisma/migrations` revisados.
- [ ] Inventario esperado generado desde ese SHA: nombres en orden, cantidad de directorios y checksum de cada `migration.sql`.
- [ ] Imagen `migrator` construida por el proceso aprobado desde ese SHA, publicada en el registro autorizado y escaneada según la política vigente.
- [ ] Tag de release registrado **junto con el digest inmutable**; el job consumirá el digest, no `latest` ni un tag mutable.
- [ ] La imagen contiene `prisma.config.ts`, `schema.prisma`, `migration_lock.toml` y exactamente el historial aprobado; su `ENTRYPOINT` es Prisma y el usuario es `node`.
- [ ] La API a desplegar proviene del mismo SHA. No hay otro job, réplica o startup que pueda ejecutar migraciones en paralelo.

### Base, compatibilidad y acceso

- [ ] Identidad productiva confirmada por cuenta/proyecto, región, endpoint, puerto, nombre de base y schema esperado (`public` actualmente), sin copiar secretos al registro.
- [ ] PostgreSQL productivo tiene versión exacta aprobada y compatible con el baseline PostgreSQL 16 probado.
- [ ] Versión exacta de pgvector confirmada compatible con `vector(768)`, HNSW y `vector_cosine_ops`; `vector` y `unaccent` están disponibles para instalación/uso.
- [ ] Diccionarios de texto de PostgreSQL y capacidad de crear/usar `public.es_unaccent` confirmados.
- [ ] Ruta desde el job a la base validada por red privada/restringida. TLS requerido y verificación de certificado configurados según el proveedor; no se asume por la forma de la URL.
- [ ] `DATABASE_URL` referencia exclusivamente la base aprobada. El operador contrastó una identidad no secreta devuelta por la base con la esperada antes de cualquier DDL.
- [ ] Rol migrador temporal separado del runtime cuando la plataforma lo permita, con login y DDL necesarios sobre el destino, sin privilegios de administración cloud ni acceso a otras bases.
- [ ] Privilegios confirmados para extensiones, tipos, configuración FTS, tablas, secuencias, índices, constraints y alteraciones incluidas en el historial. El rol runtime mantiene permisos menores.

### Estado, drift y recuperación

- [ ] Estado actual de `_prisma_migrations` exportado de forma sanitizada: `migration_name`, `checksum`, `started_at`, `finished_at`, `rolled_back_at` y `applied_steps_count`.
- [ ] No existen filas inconclusas, fallidas, marcadas como rollback, checksums vacíos ni nombres/checksums inesperados respecto del historial del release.
- [ ] Se determinó si la base es nueva, fue creada por Prisma o contiene objetos/datos previos. Cualquier baseline o drift fue revisado y aprobado por especialista.
- [ ] Drift de schema, extensiones, FTS, índices y constraints evaluado con herramientas/consultas aprobadas. No se usa `db push` para reconciliarlo.
- [ ] Riesgos sobre datos existentes revisados: unicidad, `NOT NULL`, FKs, `CHECK`, reescrituras, creación de índices, espacio libre, duración y locks.
- [ ] Backup consistente tomado según la tecnología elegida, cifrado y con retención/ubicación registradas.
- [ ] Restauración del mismo mecanismo probada recientemente en un ambiente aislado y representativo; RPO, RTO, responsable y pasos de recuperación aceptados.
- [ ] Capacidad, monitoreo y alertas activos; ventana incluye migración, validación y margen de recuperación. No se extrapolan los tiempos de la prueba local.

### Gate explícito

| Decisión | Criterio |
|---|---|
| **GO** | Todos los checks obligatorios tienen evidencia; release, plataforma, DB, seguridad, aplicación y continuidad aprobaron; no hay anomalías abiertas. Registrar hora, SHA, digest y roles aprobadores. |
| **NO-GO** | Falta evidencia, hay drift/historial inesperado, backup no restaurable, compatibilidad o TLS no confirmados, permisos dudosos, alerta activa, ventana insuficiente o no existe plan de recuperación. Detener antes del job. |

## 3. Secuencia de ejecución

> **Ejemplos, no procedimientos ejecutados.** Los comandos contienen marcadores y guardas deliberadas. Deben adaptarse al registro y orquestador aprobados. Nunca pegar una URL real en consola, argumentos, tickets o logs.

### 3.1 Construir y publicar el artefacto aprobado

El pipeline autorizado debe hacer el build desde un checkout limpio del SHA aprobado, publicar una sola imagen y devolver su digest. Ejemplo ilustrativo local, sin conexión a una base:

```powershell
$env:RELEASE_SHA = '<SHA_COMPLETO_APROBADO>'
$env:MIGRATOR_IMAGE = '<REGISTRO_AUTORIZADO>/pispiar-migrator:<TAG_INMUTABLE>'
if ($env:RELEASE_SHA -like '<*' -or $env:MIGRATOR_IMAGE -like '<*') { throw 'Completar aprobación y artefacto' }

$actualSha = (git rev-parse HEAD).Trim()
if ($LASTEXITCODE -ne 0 -or $actualSha -ne $env:RELEASE_SHA) {
    throw 'El commit actual no coincide con el release aprobado'
}
docker build --progress=plain --target migrator -f apps/api/Dockerfile -t $env:MIGRATOR_IMAGE .
docker push $env:MIGRATOR_IMAGE
docker image inspect $env:MIGRATOR_IMAGE --format '{{index .RepoDigests 0}}'
```

Registrar SHA, digest, resultado de escaneo, identidad del pipeline y manifiesto/inventario de migraciones. La promoción posterior usa `<IMAGEN>@sha256:<DIGEST_APROBADO>`.

### 3.2 Preparar el job único

1. Crear un job one-off con reintentos automáticos **desactivados** y concurrencia máxima uno.
2. Autorizar temporalmente la identidad del job en red y secretos. Recuperar `DATABASE_URL` en runtime desde el gestor aprobado; no materializarla en imagen, manifiesto versionado ni salida.
3. Confirmar por una operación de inspección aprobada la identidad no secreta de servidor/base/schema, TLS y estado previo. Comparar con el registro de GO.
4. Fijar imagen por digest, límites de recursos, timeout acorde a la ventana y captura de logs sanitizados.
5. Asegurar que la API anterior permanece estable y que el rollout de la nueva API está bloqueado hasta el gate posterior.

Contrato ilustrativo del contenedor; requiere que el orquestador inyecte manualmente el secreto y el digest aprobados:

```powershell
$env:MIGRATOR_DIGEST = '<REGISTRO>/pispiar-migrator@sha256:<DIGEST_APROBADO>'
if ($env:MIGRATOR_DIGEST -like '*<*') { throw 'Falta digest aprobado' }
if ([string]::IsNullOrWhiteSpace($env:DATABASE_URL)) { throw 'El orquestador no inyectó DATABASE_URL' }

docker run --rm --env DATABASE_URL $env:MIGRATOR_DIGEST migrate deploy
```

La forma final debe ser la equivalente nativa del orquestador, sin imprimir el entorno. Ejecutar **exactamente un job** antes del rollout. Nunca ejecutar migraciones en `ENTRYPOINT`, startup, healthcheck o cada réplica de la API; tampoco durante `docker build`.

Seguridad: Las variables de entorno de un contenedor pueden ser visibles para quienes tengan acceso privilegiado al motor Docker, incluso mediante docker inspect. En producción, utilizar el mecanismo de inyección de secretos aprobado por el orquestador y restringir los permisos de inspección y administración de contenedores. No considerar que --env DATABASE_URL oculta el secreto frente a operadores privilegiados.

### 3.3 Capturar resultado y cerrar el gate

- Registrar timestamps, SHA, digest, identificador del job, exit status, duración y nombres aplicados/pendientes, sin URL, usuario, contraseña, host sensible, tokens ni dumps.
- Exit status distinto de cero, timeout, pérdida de observabilidad o mensaje ambiguo: **STOP**. No relanzar automáticamente.
- Con exit status cero, el/la responsable de DB compara historial y schema con la evidencia previa y el inventario del release.
- Autorizar rollout sólo si las verificaciones de la sección 4 son satisfactorias y quedan aprobadas por DB, plataforma y aplicación.
- Revocar el acceso elevado/temporal del job después de recolectar evidencia, tanto en éxito como en fallo.

## 4. Verificación posterior y gate de release

Las siguientes consultas son **fragmentos ilustrativos de sólo lectura** para una sesión ya autenticada y aprobada; no incluyen comando de conexión ni destino. Adaptar a la política del proveedor y sanitizar resultados.

```sql
SELECT migration_name, checksum, started_at, finished_at,
       rolled_back_at, applied_steps_count
FROM public."_prisma_migrations"
ORDER BY migration_name;

SELECT extname, extversion
FROM pg_extension
WHERE extname IN ('vector', 'unaccent')
ORDER BY extname;
```

- [ ] Nombres y cantidad coinciden exactamente con el inventario del SHA; checksums coinciden con la evidencia aprobada.
- [ ] Cada fila tiene `finished_at`, `rolled_back_at IS NULL`, checksum no vacío y `applied_steps_count > 0`; no hay migraciones inesperadas o pendientes.
- [ ] `vector` y `unaccent` están presentes con versiones compatibles; `chunks.embedding` es `vector(768)`.
- [ ] Existe `public.es_unaccent`; `chunks.content_tsv` es `tsvector` generado y almacenado.
- [ ] Índices: `chunks_embedding_idx` (HNSW) y `chunks_area_ids_idx`, `chunks_content_fts_idx`, `chunks_content_fts_es_unaccent_idx`, `chunks_content_tsv_idx` (GIN).
- [ ] Constraints: `chunks_document_version_id_fkey`, `document_conflict_alerts_pair_order_check`, `document_conflict_alerts_resolution_check` y `document_conflict_alerts_occurrences_check`.
- [ ] Logs/monitoreo no muestran locks prolongados, saturación, errores de DB, crecimiento anómalo, réplica atrasada ni degradación.
- [ ] Desplegar la API del mismo SHA de forma controlada. Probar `/api/health/live` y una selección aprobada de lecturas/escrituras críticas, autenticación y búsqueda FTS/vectorial sin usar datos sensibles ni ejecutar seeds.
- [ ] Confirmar tasas de error, latencia, conexiones y logs de API/DB dentro de umbrales acordados.

**Aceptación:** plataforma, DB y aplicación firman la evidencia; recién entonces el responsable de release abre el rollout. Si falla cualquier check, detener o pausar el rollout y aplicar la matriz siguiente. Un exit status cero del migrador no alcanza por sí solo.

## 5. Matriz de decisión ante fallos

| Escenario | Acción inmediata | ¿Retry? | Recuperación/decisión |
|---|---|---|---|
| Red, DNS, TLS o autenticación falla **antes de DDL**, y se demuestra que `_prisma_migrations`/schema no cambiaron | **STOP**; conservar evidencia sanitizada, corregir únicamente la causa de acceso y repetir preflight completo. | Sólo con causa identificada, estado sin cambios y nueva aprobación. Nunca automático. | No restaurar si se demostró ausencia de cambios. Si no puede demostrarse, tratar como estado incierto. |
| Falta `vector`/`unaccent` o hay privilegios insuficientes | **STOP**; no ampliar privilegios improvisadamente ni cambiar SQL versionado. | Sólo después de validar compatibilidad, otorgar el mínimo permiso por cambio aprobado y confirmar si hubo DDL. | Especialista inspecciona estado. Si hubo cambios parciales, seguir el escenario siguiente. |
| Migración fallida con DDL posiblemente parcial, timeout o conexión perdida durante DDL | **STOP**; bloquear job y rollout, preservar logs/estado y convocar responsable de DB. | **No** hasta conocer transacciones, objetos, datos y fila Prisma afectados. | Elegir mediante revisión experta: restaurar el backup probado o preparar un forward-fix versionado, revisado y ensayado. No limpiar ni relanzar a ciegas. |
| Drift, objetos preexistentes o historial/checksum inesperado | **STOP / NO-GO**; no usar `db push`, editar migraciones aplicadas ni falsear historial. | No mientras exista discrepancia. | Comparar DB, release y procedencia. Definir baseline/reconciliación sólo con aprobación de DB y aplicación; `migrate resolve` requiere revisión experta específica. |
| API falla después de migraciones exitosas | Detener/pausar rollout; mantener evidencia y evaluar compatibilidad del binario anterior con el schema nuevo. | El migrador no se repite: primero confirmar que no hay migraciones pendientes. | Rollback de aplicación sólo si es compatible; si no, forward-fix de aplicación/schema aprobado o restauración coordinada. Restaurar DB puede perder escrituras posteriores y exige detener tráfico según el plan. |

Si el punto exacto del fallo es desconocido, clasificarlo como **posible DDL parcial**. La limpieza de recursos del test local no demuestra que sea seguro limpiar objetos productivos.

## 6. Política de recuperación

- Un rollback de imagen/API **no revierte** migraciones de base. Prisma no aporta down migrations automáticas para este historial.
- No ejecutar automáticamente `migrate reset`, `migrate dev`, `db push`, seeds, SQL destructivo, borrado de objetos ni restauraciones.
- Restaurar requiere: backup identificable y consistente, prueba reciente de restaurabilidad, claves/accesos disponibles, RPO/RTO aceptados, destino y punto temporal aprobados, estimación de pérdida de escrituras, congelamiento o redirección de tráfico, y responsables de DB/negocio presentes.
- Antes de restaurar, preservar evidencia del incidente y decidir qué pasa con escrituras posteriores al backup. Ensayar primero cuando el tiempo y el plan lo permitan; validar integridad e historial antes de reabrir tráfico.
- Un forward-fix debe ser una migración nueva, mínima, revisada, ensayada con una copia representativa y desplegada por el mismo gate. No modificar una migración ya aplicada.
- `prisma migrate resolve` no corrige por sí mismo el schema: sólo considerar su uso tras diagnóstico experto, comparación exacta entre SQL/DB/historial, plan escrito, ensayo y aprobación conjunta de DB, aplicación y release. Este runbook no ordena ejecutarlo.

## 7. Seguridad, evidencia, monitoreo y costos

### Seguridad y evidencia

- `DATABASE_URL` vive en el gestor de secretos y se inyecta sólo al job autorizado. Prohibido incluirla en argumentos visibles, `docker inspect` compartido, logs, capturas, archivos `.env`, artefactos o Git.
- Usar identidad individual/MFA para operadores y credencial efímera para el job cuando la plataforma lo permita. Limitar red, base, schema, duración y acciones; revocar permisos elevados al terminar.
- Desactivar trazas de shell que impriman comandos/entorno. Sanitizar mensajes y conservar únicamente SHA, digest, job, timestamps, duración, exit status, inventario y resultados no sensibles.
- Definir acceso y retención de evidencias. Ante sospecha de filtración: detener, revocar/rotar, auditar accesos e informar por el proceso de incidentes; borrar el log no revoca el secreto.

### Continuidad y observabilidad

- Retención de backups, cifrado, ubicación/cuenta, inmutabilidad si aplica y prueba periódica de restauración deben estar aprobados; una marca de “backup exitoso” sin restore test no alcanza.
- Alertar por fallo/timeout del job, locks prolongados, conexiones, CPU/memoria/almacenamiento, errores PostgreSQL/API, réplica atrasada y duración fuera del umbral acordado.
- Registrar duración de preflight, migración, verificaciones y eventual recuperación. Establecer umbrales con ensayos sobre datos representativos, no con los ~1,5 s locales sobre base vacía.

### Costo controlado

- Cotizar con fuentes vigentes la ejecución del job, capacidad temporal de DB, almacenamiento/retención de backups, restore tests, logs/métricas y transferencia entre región/cuenta/proveedor. No se asumen precios ni gratuidad de AWS.
- Reutilizar el artefacto inmutable, aplicar retención de logs/backups acorde al riesgo y apagar recursos temporales sólo después de verificar evidencia y restaurabilidad.
- Las optimizaciones de costo no justifican omitir backup probado, TLS, observabilidad, ventana suficiente ni capacidad de recuperación. Configurar alertas presupuestarias recordando que una alerta puede no ser un límite duro.

## 8. Handoff a plataforma AWS y bloqueos

El/la responsable de AWS debe entregar, sin exponer secretos:

- [ ] Cuenta/proyecto, región y ambientes; servicio/orquestador elegidos y responsables operativos.
- [ ] Registro de imágenes, política de tags/digests, pipeline de build/publicación, escaneo y permisos de pull.
- [ ] Tipo/versión exacta de PostgreSQL y pgvector, soporte de `unaccent`, parámetros relevantes, schema/search path y límites/capacidad.
- [ ] Identidad no secreta de la DB, conectividad del job, DNS, reglas de red y mecanismo TLS con validación de certificado.
- [ ] Gestor de secretos, identidad runtime del job, método de inyección, rotación/revocación y separación entre rol migrador y rol API.
- [ ] Orquestación del job único: concurrencia, retries desactivados, timeout, salida/exit status, bloqueo previo al rollout y revocación posterior.
- [ ] Backup/PITR disponible, retención, cifrado, RPO/RTO, última restauración probada, tiempo medido y procedimiento autorizado.
- [ ] Monitoreo, umbrales, alertas, retención/sanitización de logs, tablero durante la ventana y canal de incidentes.
- [ ] Estrategia de rollout/rollback de API, compatibilidad evaluada, smoke tests, ventana, congelamiento de cambios y aprobadores GO/NO-GO.
- [ ] Estimación y autorización de costos para DB, backups/restores, job, observabilidad y transferencia.

### Decisiones no resueltas que bloquean producción

Siguen pendientes la topología AWS, versiones/digests productivos, identidad de la base, TLS, permisos, estado/drift real, estrategia y prueba de backup/restauración, ventana basada en datos representativos, orquestador, monitoreo, costos y compatibilidad de rollback. Hasta resolverlos con evidencia, la decisión es **NO-GO**.
