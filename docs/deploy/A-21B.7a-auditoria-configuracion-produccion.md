## 3. Bloqueos de arranque y capacidades degradables

| Momento | Bloqueo confirmado | No bloquea el arranque, pero bloquea/degrada una capacidad |
|---|---|---|
| API startup | Falta `DATABASE_URL`; conexión PostgreSQL fallida en `onModuleInit`; `JWT_SECRET` ausente/vacía; falta `S3_BUCKET` en producción; bucket sin región; `S3_ENDPOINT` no parseable; `S3_FORCE_PATH_STYLE` inválido; `REDIS_URL` inválida para el adaptador BullMQ. | Redis ausente puede usar localhost y fallar asíncronamente/al primer uso; credenciales/política S3 no se prueban; Resend/`FRONTEND_URL` se validan al crear una invitación; Gemini se valida al ejecutar chat/embedding. |
| Web build | `API_URL` ausente con `NODE_ENV=production`; la CI lo confirma al inyectar `http://localhost:3000` sólo para construir. | Destino mal formado o HTTP puede pasar la validación actual y quedar en el rewrite. |
| Runtime web | Next necesita el rewrite generado y conectividad al backend. | **Inferido:** cambiar sólo `API_URL` después de construir no es un contrato de promoción seguro; la forma exacta depende del artefacto/hosting, hoy no definido. |
| Función invitaciones | Ninguna de sus variables detiene la API. | Provider distinto de `resend`, clave/remitente faltante o `FRONTEND_URL` inválida produce 503 antes de persistir. Es fail-closed, pero tardío. |
| IA/procesamiento | No hay gate de clave/modelo/cuota. El worker queda habilitado por defecto. | Chat y embeddings fallan al primer uso si proveedor/clave/modelo no están operativos; apagar worker puede acumular trabajos en cola. |

El endpoint `/api/health/live` sólo prueba que el proceso HTTP responde; no verifica PostgreSQL, Redis, S3, Resend, Gemini ni la capacidad del worker. Esto está correctamente advertido por la [guía Docker](./A-21B.4-guia-imagen-api-y-smoke-test.md), pero todavía no existe readiness de dependencias.

## 4. Hallazgos de seguridad y operación

| Prioridad | Hallazgo | Clase | Impacto y salvaguarda existente |
|---|---|---|---|
| **P0** | `REDIS_URL` cae a `redis://localhost:6379` también en producción. | Confirmado | Puede apuntar al destino incorrecto o dejar rate limiting/colas sin servicio. Auth falla cerrada ante errores de Redis, lo cual protege contra bypass pero afecta disponibilidad. Debe rechazarse el fallback productivo. |
| **P0** | Rate limiting y metadatos usan `req.ip`, pero la API no configura `trust proxy`. | Confirmado; impacto AWS inferido | Detrás de proxy/LB, puede ver la IP del proxy y agrupar usuarios. Habilitar confianza indiscriminada permitiría spoofing. Hace falta una política exacta según saltos/red del despliegue y pruebas desde Internet. |
| **P1** | No hay validación productiva centralizada; las comprobaciones están dispersas y varias son tardías. | Confirmado | Una API puede quedar “viva” con invitaciones o IA inutilizables. Sí existen gates valiosos para DB/JWT/S3 y fail-closed de invitaciones/rate limit; deben conservarse. |
| **P1** | `JWT_SECRET` sólo se valida por presencia. | Confirmado | Una cadena débil pasa startup. Falta requisito de longitud/entropía, origen en secret manager y plan de rotación; no se observó fallback inseguro. |
| **P1** | TLS no se exige para `DATABASE_URL`, `REDIS_URL`, `S3_ENDPOINT` ni `API_URL`. | Confirmado; exigencia final no verificada | El repositorio admite `postgresql://`, `redis://` y HTTP. Desarrollo lo necesita, pero producción debe validar la modalidad aprobada y certificados sin inventar parámetros del proveedor. |
| **P1** | `API_URL` acepta cualquier texto no vacío y `S3_ENDPOINT` cualquier URL parseable. | Confirmado | Pueden admitir credenciales, esquema inseguro o path inesperado. `FRONTEND_URL`, en cambio, ya valida HTTPS y rechaza credenciales/query/fragmento: no duplicar ese arreglo. |
| **P1** | Swagger se publica siempre en `/api/docs`; no hay toggle ni control propio. | Confirmado | Exposición y acceso quedan librados a la red/proxy. Definir si se deshabilita o restringe en producción. |
| **P1** | No se observan `helmet`, HSTS/CSP ni política de proxy en la API. | Confirmado; responsabilidad final inferida | Pueden aplicarse en Nest o en el edge, pero debe existir una única decisión verificable. No se marca CORS como defecto: el flujo web actual usa rewrite same-origin. |
| **P2** | `PORT`, `APP_TIMEZONE` y `PROCESSING_WORKER_ENABLED` no tienen validación estricta. | Confirmado | Typos pueden producir socket inesperado, error tardío de fechas o worker habilitado involuntariamente. |
| **P2** | `AI_PROVIDER` está documentada pero no selecciona nada. | Confirmado | Da una falsa impresión de portabilidad/configuración. Removerla del contrato o implementar selección en una tarea funcional explícita; no es un bloqueo actual. |

### Controles ya implementados que deben preservarse

- Cookie refresh `HttpOnly`, `Secure` en producción, `SameSite=Lax` y path `/api/auth`; el JWT de acceso queda en memoria del navegador.
- Producción fuerza sesión real: `NEXT_PUBLIC_REAL_AUTH=false` no activa simulación.
- Invitaciones productivas no aceptan provider local; `FRONTEND_URL` no se construye desde `Host` y exige HTTPS.
- Rate limiting de autenticación falla cerrado ante Redis caído y evita email/token en claro en sus claves.
- S3 en producción no cae a memoria; la imagen corre como usuario `node`; `.dockerignore` excluye `.env` reales.
- DTOs globales usan whitelist y rechazan campos desconocidos.

## 7. Tareas mínimas propuestas

### A-21B.7b — P0/P1: contrato y validación productiva fail-fast

1. Incorporar un esquema único de configuración de API que preserve gates actuales y, con `NODE_ENV=production`, rechace localhost/default de Redis, secreto JWT débil, URLs/protocolos no aprobados, timezone inválida, booleanos desconocidos y valores requeridos por capacidades habilitadas.
2. Separar variables core de capacidades (`invitations`, `processing`, `AI`) y validar al startup las que el release declara habilitadas; mensajes sin valores sensibles.
3. Definir una variable/política segura de proxy acorde a la topología aprobada, con tests de IP real y spoofing. No habilitar `trust proxy=true` genérico.
4. Agregar control explícito de Swagger y cabeceras de seguridad en API o documentar/ensayar su aplicación obligatoria en el edge.
5. Validar `API_URL` para el build productivo y documentar si el artefacto web es por ambiente o admite configuración runtime real.

### A-21B.7c — P1/P2: pruebas de readiness y contrato de entrega

1. Agregar tests/config smoke sin credenciales reales: tabla de casos válidos/inválidos para API y build web; comprobar que producción nunca usa simulación, storage en memoria ni Redis local.
2. Diseñar readiness separado de liveness para dependencias obligatorias, con timeouts y sin causar escrituras/costos inesperados. Resend/Gemini/S3 requieren estrategia de preflight acordada, no llamadas automáticas ciegas.
3. Sincronizar `.env.example`, `apps/web/.env.example`, README y documentación vigente; marcar `AI_PROVIDER` como no operativa o retirarla del contrato y agregar variables hoy ausentes del ejemplo.
4. Versionar el contrato del artefacto web y del orquestador: qué variables se fijan en build, cuáles en runtime, promoción por ambiente, health/readiness y evidencia sanitizada.
5. Ejecutar pruebas controladas de proxy/cookies/TLS, Redis fail-closed, invitaciones, S3 y Gemini en staging antes del gate productivo.

## 8. Decisiones dependientes de AWS/proveedores

Estas decisiones no se resuelven con cambios de repositorio y permanecen **no verificadas**:

- Servicio, cuenta, región, DNS, certificados, terminación TLS, cantidad de proxies/LB y rangos confiables.
- Hosting/build de Next y estrategia de promoción de `API_URL` entre ambientes.
- PostgreSQL: endpoint privado, CA/modo TLS, versión, schema, backup/restauración y rol runtime.
- Redis: servicio, TLS (`rediss://` si corresponde), autenticación, aislamiento, persistencia, timeouts y disponibilidad.
- S3: bucket/región, endpoint si no es AWS, cifrado, CORS, lifecycle y rol IAM mínimo para `Get/Put/Delete`/presign.
- Resend: dominio/remitente verificado, cuota, reputación, secretos y observabilidad de entrega.
- Gemini: proyecto, modelos habilitados, cuota/presupuesto, región/política de datos y rotación de clave.
- Dónde se aplican Swagger, HSTS/CSP y otras cabeceras: aplicación o edge; debe evitarse tanto el vacío como la configuración contradictoria.

El repositorio sí debe exponer controles configurables y validarlos; AWS debe aportar los valores, identidades, red y evidencia operativa. Ningún default local constituye una decisión de infraestructura.
