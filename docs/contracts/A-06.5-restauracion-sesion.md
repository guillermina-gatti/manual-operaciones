## 1. Problema concreto

Tras iniciar sesión, la API responde `POST /api/auth/login` con un `accessToken` y el resumen de usuario `{id,name,email,role}`. Guarda el refresh token en una cookie `httpOnly`, `SameSite=lax`, `Path=/api/auth` y `Secure` en producción.

Al recargar la web, el access token de corta duración (15 minutos) que está únicamente en memoria desaparece. El navegador todavía puede conservar la cookie de refresh. `POST /api/auth/refresh` rota la cookie y devuelve actualmente **solo** `{accessToken}`. La pantalla necesita además el `id`, `name` y `role` actuales para recuperar `SessionUser` y mostrar la navegación correcta.

La implementación de desarrollo (`apps/web/lib/session/simulated-session.tsx`) resuelve la identidad recurriendo a fixtures y `sim-session` (ID en `localStorage`), pero **se desactiva en producción**. No se debe trasladar esa dependencia al login real.

## 3. Opciones evaluadas

| Opción | Ventajas | Costos/riesgos | Evaluación |
|---|---|---|---|
| **A. Agregar `user` a la respuesta de `POST /api/auth/refresh`** | La API ya consulta usuario vigente; una sola petición al recargar; reutiliza cookies, seguridad y service existentes; no requiere ruta adicional | Cambiar contrato, Swagger y expectativas de tests; comunicar nueva forma a consumidores | **RECOMENDADA para el MVP** |
| **B. Crear `GET /api/auth/me` protegido con Bearer** | Endpoint de perfil reusable, lectura explícita de identidad | Al recargar exige `refresh` + `me`: dos peticiones; más controller, guard, tests y escenarios de error; innecesario para la necesidad actual | Reservar para necesidad funcional adicional |
| **C. Guardar perfil de usuario en `localStorage` y leer `sub` del JWT** | Pocos cambios del servidor | Identidad y rol mostrados podrían quedar desactualizados; duplicación de fixtures/almacenamiento; no sustituye autorización real | **No recomendar para producción** |

### Decisión técnica propuesta

**Ampliar de forma aditiva `POST /api/auth/refresh`** para que la respuesta `200` incluya un resumen de usuario actual, exactamente con los mismos campos públicos que `login`:

```http
POST /api/auth/refresh HTTP/1.1
Cookie: refreshToken=<cookie-httpOnly-que-envia-el-navegador>
Accept: application/json
```

Respuesta propuesta:

```json
{
  "accessToken": "<nuevo-JWT>",
  "user": {
    "id": "11111111-1111-4111-8111-111111111111",
    "name": "Usuario de ejemplo",
    "email": "usuario@ejemplo.test",
    "role": "EMPLOYEE"
  }
}
```

El refresh token **no** se devuelve en el cuerpo JSON; se rota en la cookie `httpOnly` como ahora. Se excluyen `passwordHash`, IDs de sesiones, `isActive`, metadatos internos, áreas y otros datos no solicitados. El front usará solo `id`, `name`, `role` para el `SessionUser` existente. `email` se incluye para mantener paridad con la respuesta de login, no como dato de autorización.

Este contrato es **aditivo**: el selector de desarrollo actual únicamente lee `accessToken` de `refresh`, por lo que puede ignorar `user`, pero habrá que ajustar los tests que comparan exactamente la respuesta.

**No se necesita `GET /api/auth/me` para A-08.** El bloque A-07 queda **NO REQUERIDO por ahora**, condicionado a un caso de uso posterior específico. No se cierra como «implementado».

## 4. Comportamiento esperado para la sesión web real (A-08; NO implementar en A-06.5)

```text
El navegador abre/recarga una ruta privada
  -> SessionProvider queda en loading; no muestra contenido privado todavía
  -> POST /api/auth/refresh con credentials: 'same-origin'
    -> 200 + nuevo accessToken + user: token solo en memoria, user real, status ready
    -> 401: user null, status ready, presentar login (sin volver a intentar en bucle)
    -> error de red/5xx: mantener estado de error recuperable y ofrecer reintento;
       no interpretarlo automáticamente como credenciales inválidas

Login manual -> POST /api/auth/login -> guardar accessToken en memoria y user de respuesta
Logout -> limpiar estado local y pedir POST /api/auth/logout para revocar cookie/sesión
```

- Las llamadas de autenticación se hacen con `fetch` directo a `/api/auth/...` y **no mediante `apiClient`** para evitar dependencia circular (el propio `apiClient` pide cabeceras a la sesión).
- Las páginas actuales importan la sesión desde `@/lib/session`; **preservar ese punto de entrada y las firmas usadas por Matías**. Reemplazar la implementación de desarrollo al final del ciclo de A-08 a A-10, no en este PR documental.
- El access token permanece **solo en memoria**: jamás `localStorage`, `sessionStorage`, URLs o logs. La cookie de refresh permanece `httpOnly` y no se intenta leer desde JS.
- Con refresh rotativo, las llamadas concurrentes **dentro de la misma pestaña** deben compartir una única promesa (single-flight). El código actual de desarrollo ya tiene un patrón `refreshing` reutilizable conceptualmente.
- La concurrencia **entre pestañas** requiere una revisión separada antes de defender el login productivo: si dos pestañas rotan simultáneamente la misma cookie, existe riesgo de fallos de sesión o detección de reutilización. Evitar inventar una solución compleja sin reproducir el caso.
- Si cambian los roles, el backend aplica los permisos vigentes en cada petición; el resumen de la interfaz se actualizará con el siguiente refresh. La UI no es la barrera de seguridad.
- Cualquier `proxy.ts` que se agregue debe respetar el rewrite `/api` y la prueba de carga de **10 MB** de la Spec 002/T26. En producción confirmar que la cookie efectivamente llega a través de Next.js y HTTPS.

## 5. Comportamientos HTTP y seguridad

| Caso | Respuesta | Efecto esperado |
|---|---|---|
| Cookie válida, sesión activa, usuario activo | 200 `{accessToken,user}` y rotación de cookie | Restaurar identidad real |
| Sin cookie, cookie inválida o vencida | 401 (respuesta opaca existente) | Quedar sin sesión; mostrar login |
| Usuario desactivado | 401 y revocación de nueva sesión según lógica actual | No exponer su perfil |
| Token reutilizado / carrera en rotación | Mantener tratamiento existente de `AuthService.refresh` | No relajar controles actuales |
| Falla de BD/infraestructura | Error controlado; no declarar usuario logueado sin validar | Ofrecer reintento cuando sea recuperable |
| Respuesta exitosa | Sin `refreshToken` en JSON; sin hashes ni datos internos | Mínima exposición |

**Precaución adicional para despliegue (fuera de A-06.5):** revisar `SameSite`, `Secure`, `Path`, origen permitido y riesgos CSRF de endpoints basados en cookies. Los flujos del navegador deben usar rutas relativas del mismo origen. No cambiar flags de cookies ni CORS de manera improvisada durante esta tarea documental.

## 7. Criterios Given–When–Then para el PR funcional futuro

1. **Dado** un usuario activo con cookie válida, **cuando** hace refresh, **entonces** recibe token nuevo, `user` con nombre y rol vigentes y cookie rotada.
2. **Dado** un usuario cuyo rol cambió en DB, **cuando** refresca, **entonces** la respuesta muestra el rol nuevo; el backend ya aplica permisos vigentes sin esperar al refresh.
3. **Dada** una cuenta desactivada, **cuando** intenta refrescar, **entonces** obtiene 401 y no se envían datos de perfil.
4. **Dada** una cookie ausente/expirada, **cuando** se restaura la página, **entonces** la UI ofrece login y no aparece contenido privado.
5. **Dadas** dos peticiones 401 concurrentes en una pestaña, **cuando** se renuevan, **entonces** se ejecuta una única rotación de cookie, no dos.
6. **Dado** un logout exitoso, **cuando** recarga la página, **entonces** no se restaura sesión.
7. **Dada** una respuesta 200, **entonces** nunca contiene `refreshToken`, `passwordHash`, secretos ni datos internos.

**Pruebas para el futuro PR funcional:** `pnpm --filter api lint`, `pnpm --filter api test`, `pnpm --filter api build`; luego `pnpm --filter api test:e2e` con servicios necesarios; cuando A-08 esté listo, `pnpm --filter web test` y `pnpm --filter web test:e2e`.
