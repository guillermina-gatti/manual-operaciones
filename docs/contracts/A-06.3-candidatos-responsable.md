## 1. Objetivo y límites

Especificar cómo obtiene la web los usuarios elegibles para ser responsables de un documento en función de las áreas seleccionadas. La regla existente de Documentos es: un responsable **ADMIN** puede ser elegido con independencia de sus áreas; otro responsable debe compartir **al menos un área** con el documento. La consulta real debe excluir cuentas inactivas.

**Alcance:** URL, método, autorización, query, respuesta mínima, reglas de selección y errores verificables. **Fuera de alcance:** crear `UsersController`, cambiar Prisma, sustituir fixtures web, modificar `OwnerField`, introducir búsquedas generales de usuarios, alterar la política de Documentos o resolver `UsersDirectory.getNames(ids)` (reservado para A-06.4).

## 3. Contrato HTTP propuesto

| Aspecto | Propuesta A-06.3 |
|---|---|
| Método y ruta | `GET /api/users` |
| Consulta completa de ejemplo | `/api/users?areaIds=UUID_A&areaIds=UUID_B` |
| Codificación de varias áreas | **Repetir** la clave `areaIds` una vez por UUID; no usar CSV ni JSON en un único parámetro |
| Autenticación | `Authorization: Bearer <accessToken>`; cuenta autenticada y activa |
| Rol autorizado | **Solo `ADMIN`** para consultar candidatos de asignación de documentos |
| Sin `areaIds` | `400 Bad Request`; la web no debe llamar sin áreas elegidas |
| `areaIds` | Uno o más UUID válidos; duplicados permitidos en la entrada y deduplicados en el servidor |
| Áreas inexistentes o inactivas | **Propuesta:** `400 Bad Request` sin revelar datos de terceros; validar la selección completa antes de listar candidatos |
| Parámetros ajenos | `400 Bad Request`; no admitir `includeInactive`, filtros arbitrarios ni paginación no acordada |
| Usuarios elegibles | Usuarios **activos** que compartan al menos un área activa de la solicitud, **más todos los usuarios activos con rol ADMIN** |
| Usuarios excluidos | Cuentas inactivas; usuarios no ADMIN sin áreas en común; pertenencias solo a áreas inactivas |
| Respuesta `200` | **Array JSON directo** de objetos `{id, name, role}` |
| Unicidad | Un objeto por `User.id`, aunque pertenezca a varias áreas de la consulta |
| Orden propuesto | Por `name` ascendente y luego `id` ascendente, estable |
| Resultado vacío | `200 OK` y `[]`; no `404`. **Nota:** en la política propuesta, el ADMIN solicitante activo también es candidato, por lo que normalmente habrá al menos uno |
| Datos que no deben devolverse | `email`, `passwordHash`, `areaIds`, sesiones, tokens, fechas, estado, relaciones y otros campos internos |
| Uso de datos | Ayuda a elegir un candidato; **no sustituye** la autorización/validación de responsables de Documentos en el momento de guardar |

**Justificación del permiso ADMIN:** el único consumidor previsto del listado de candidatos es `OwnerField`, integrado en la carga administrativa de documentos. La matriz de permisos no habilita a SUPERVISOR ni EMPLOYEE para cargar documentos ni consultar directorios generales de usuarios. A diferencia del listado de áreas (A-06.2), aquí se exponen nombres de personas. **Validar este alcance con Equipo C** antes de considerar el contrato aceptado.

**Propuesta sobre la selección de áreas:** `areaIds` vacío debe producir `400`, no un listado general de ADMIN; los UUID desconocidos o inactivos se tratan como selección inválida. Esta validación se propone para impedir que un selector con información obsoleta genere una nueva asignación incorrecta. No se alteran las referencias históricas ni los puertos de Documentos.

## 4. Ejemplos del contrato (no ejecutados)

**Solicitud con dos áreas** (valores de los fixtures usados en desarrollo):

```http
GET /api/users?areaIds=0a000000-0000-4000-8000-000000000001&areaIds=0a000000-0000-4000-8000-000000000002 HTTP/1.1
Authorization: Bearer <token-de-admin>
Accept: application/json
```

**`200 OK` — respuesta ilustrativa** (los nombres son fixtures; no afirman la existencia de estos datos en producción):

```json
[
  {"id":"0b000000-0000-4000-8000-000000000001","name":"Ana Administradora","role":"ADMIN"},
  {"id":"0b000000-0000-4000-8000-000000000003","name":"Elena Empleada de Ventas","role":"EMPLOYEE"},
  {"id":"0b000000-0000-4000-8000-000000000005","name":"Emilio Empleado de Operaciones","role":"EMPLOYEE"},
  {"id":"0b000000-0000-4000-8000-000000000002","name":"Sergio Supervisor de Ventas","role":"SUPERVISOR"},
  {"id":"0b000000-0000-4000-8000-000000000004","name":"Sofía Supervisora de Operaciones","role":"SUPERVISOR"}
]
```

**Solicitud solo de Ventas:** `GET /api/users?areaIds=0a000000-0000-4000-8000-000000000001`. Debería incluir a la ADMIN, a Sergio y a Elena, y excluir a Sofía y a Emilio si únicamente pertenecen a Operaciones.

**Respuesta vacía:** si, por un cambio futuro de reglas, no hubiera candidatos, el contrato prevé `200 OK` con `[]`. **Con la regla actual y un ADMIN activo solicitante, se espera al menos ese ADMIN.** **Sin áreas en la solicitud:** `400`, no `[]`.

## 5. Errores HTTP previstos

| Estado | Motivo | Respuesta esperada |
|---|---|---|
| `200 OK` | ADMIN activo; áreas válidas; consulta exitosa | Array directo; puede estar vacío |
| `400 Bad Request` | Falta `areaIds`, UUID inválido, formato CSV en vez de repetidos, área desconocida/inactiva o query no admitida | Error de validación sin datos personales ni información interna |
| `401 Unauthorized` | Ausencia de token, token inválido o cuenta solicitante desactivada | Guard de autenticación; no revelar candidatos |
| `403 Forbidden` | SUPERVISOR o EMPLOYEE autenticado intenta consultar la lista | Guard de rol; no revelar candidatos |
| `404 Not Found` | No corresponde al listado; los resultados sin coincidencias son `[]` | No usar como señal de vacío |
| `503 Service Unavailable` | Falla temporal de infraestructura | **Objetivo de implementación**, requiere revisar tratamiento de errores incluso en guards; no convertir errores en `[]` |

**Formato de error propuesto:** convención HTTP de Nest (`statusCode`, `message`, `error`) compatible con el cliente web. La ruta aún no existe: ninguno de estos códigos ha sido probado para este endpoint.

## 6. Seguridad y coherencia de la selección

1. El filtro de usuarios activos, la elegibilidad por áreas y el rol del **solicitante** se verifican en backend; no confiar en que el frontend ya haya aplicado `filterOwnerCandidates`.
2. No publicar correos ni hashes ni un endpoint general de búsqueda por nombres: solo devolver los tres campos que consume `OwnerField`.
3. La consulta considera únicamente relaciones con áreas **activas**. El ADMIN candidato es excepción a la coincidencia de áreas, **pero nunca** a la regla de `User.isActive`.
4. Ante usuarios repetidos por varias relaciones `UserArea`, devolverlos solo una vez. Si dos personas tienen igual nombre, ordenarlas por `id` sin desambiguar mediante datos privados.
5. `OwnerField` vuelve a consultar cuando cambian las áreas. **El servidor de Documentos debe revalidar** que el `ownerId` sigue siendo válido en el instante de guardar: elegir un candidato no es una autorización permanente.
6. Si un ADMIN consultante no tiene áreas asignadas, puede igualmente consultar candidatos para áreas activas explícitamente solicitadas; su permiso depende de su rol global.
7. No añadir un mecanismo para resolver nombres históricos o listas arbitrarias de IDs aquí: `getNames(ids)` se tratará específicamente en **A-06.4**, porque presenta riesgos distintos de enumeración.

**Brecha registrada desde A-06.1:** `PrismaUsersDirectory.findById` del módulo de Documentos no filtra actualmente `User.isActive`. Por ello, **un resultado correcto de este nuevo listado no garantiza** que un `ownerId` enviado manualmente sea rechazado por el módulo de Documentos. La corrección y el criterio para conservar responsables históricos requieren coordinación con C; **no cambiar aquí su puerto ni su política**.

## 7. Pruebas de aceptación para A-12, no ejecutadas ahora

- [ ] ADMIN activo consulta una sola área válida y recibe los usuarios activos de esa área más todos los ADMIN activos.
- [ ] Con dos `areaIds` repetidos, el resultado es la unión de usuarios elegibles y no contiene duplicados.
- [ ] Con un `areaIds` duplicado, no aparecen filas repetidas.
- [ ] Un usuario que solo pertenece a otra área no aparece; ADMIN activo sin áreas sí aparece.
- [ ] Usuario inactivo, incluso si es ADMIN, no aparece.
- [ ] Usuario con relación únicamente a áreas inactivas no aparece por esa relación.
- [ ] Respuesta limitada a `id`, `name`, `role`, con `role` en `ADMIN | SUPERVISOR | EMPLOYEE`.
- [ ] Resultado ordenado de forma estable; el contrato conserva `200 []` como respuesta vacía eventual, aunque no se espera mientras un ADMIN activo pueda consultar.
- [ ] Sin `areaIds`, UUID inválido, CSV, área inexistente o inactiva: `400` según la propuesta.
- [ ] Sin autenticación o cuenta solicitante desactivada: `401`; SUPERVISOR/EMPLOYEE activos: `403`.
- [ ] Falla de BD: error controlado; nunca `200 []` como falso resultado.
- [ ] La interfaz web `listOwnerCandidates(areaIds): Promise<DirectoryUser[]>` sigue siendo compatible sin tocar `OwnerField`.
- [ ] No se modifican permisos ni contratos de Documentos/C; la carga sigue revalidando `ownerId`.
