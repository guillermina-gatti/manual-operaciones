- **Revisión:** 31/10/2026
- **Base inspeccionada:** `develop@22b28e49ec852f4cf368e4969c1a8e4c473745d9` (PR #21 de A-06.2 fusionado)
- **Estado vigente (01/11/2026):** Equipo C ratificó el acceso exclusivo de `ADMIN`; A-12 (PR #26) implementó el endpoint, T29 (PR #28) conectó sus candidatos reales y A-13 (PR #30) amplió el directorio interno. Las listas originales de criterios se conservan como antecedentes, no como estado actual.

> **Cambio respecto del 30/10:** el Equipo C confirmó HTTP `400` cuando no se indican áreas o cuando alguna no existe o está inactiva; no requiere paginación ni búsqueda para el MVP. Confirmó que las nuevas asignaciones deben excluir responsables inactivos y que los vínculos históricos deben conservarse. Esto último exige exponer `isActive` en el **directorio interno de Documentos**, que es distinto del listado HTTP de candidatos.

## 1. Objetivo y alcance

El formulario administrativo necesita listar personas elegibles como responsables de un documento según las áreas seleccionadas. La lista ayuda a elegir, pero **no autoriza** a guardar una asignación: Documentos debe revalidar el `ownerId` en el servidor.

Esta revisión define método, parámetros, respuesta mínima, selección, errores y casos de aceptación futuros. No crea endpoints, modifica Prisma, cambia puertos internos, sustituye fixtures, actualiza `OwnerField` ni altera las reglas de escritura de Documentos. La resolución de nombres históricos de usuarios corresponde a **A-06.4**.

## 2. Interfaces existentes y separación de responsabilidades

- **Directorio web:** `apps/web/lib/directory/users-directory.ts` expone `listOwnerCandidates(areaIds): Promise<DirectoryUser[]>`, con `{id,name,role}`; y `getNames(ids)` para resolver nombres históricos.
- **Consumo web:** `OwnerField.tsx` consulta candidatos cuando hay áreas seleccionadas, vuelve a consultar al cambiarlas y actualmente borra una elección que no aparece en la nueva lista.
- **Implementación vigente:** T29 integra `listOwnerCandidates()` con la API real; `getNames(ids)` sigue temporalmente respaldado por fixtures hasta que C adapte los DTO históricos. A-12 ya expone `GET /api/users`.
- **Puerto interno vigente:** A-13 amplió `findById(id)` con `{id,name,role,areaIds,isActive}` y conserva la resolución por ID de usuarios inactivos.
- **Módulo de Documentos:** `DocumentWriteSteps.assertOwnerCanSeeDocument` valida existencia y acceso por áreas, pero no comprueba todavía actividad del responsable. Matías asumió la corrección de esa validación del lado de C, una vez disponible el dato.

**No confundir interfaces:** la API de candidatos sirve para **seleccionar un responsable nuevo**; el puerto `findById` permite a Documentos **validar una asignación solicitada**; `getNames(ids)` sirve para **mostrar nombres ya referenciados**. Ninguna de las tres tareas reemplaza a las otras.

## 3. Contrato HTTP para A-12

| Aspecto | Definición |
|---|---|
| Método y ruta | `GET /api/users` |
| Ejemplo de URL | `/api/users?areaIds=UUID_A&areaIds=UUID_B` |
| Autenticación | `Authorization: Bearer <accessToken>`; cuenta solicitante activa |
| Rol del solicitante | **Solo `ADMIN`**, confirmado por Equipo C e implementado en A-12 (PR #26) |
| Parámetro requerido | `areaIds`, una o más veces; **un UUID por ocurrencia** |
| Varias áreas | Repetir la clave `areaIds`; no CSV ni JSON en un único parámetro |
| Duplicados | Aceptarlos y deduplicar los UUID antes de consultar |
| Sin `areaIds` | `400 Bad Request` **confirmado por C** |
| Área inexistente o inactiva | `400 Bad Request` **confirmado por C**, incluso si las demás son válidas |
| UUID inválido o query ajena | `400 Bad Request` propuesto; no aceptar filtros, búsqueda, paginación ni `includeInactive` |
| Usuarios elegibles | Usuarios **activos** de al menos una de las áreas activas indicadas, más usuarios **activos** con rol `ADMIN` |
| Usuarios excluidos | Cuentas inactivas, usuarios no ADMIN sin áreas en común, relaciones solo con áreas inactivas |
| Respuesta `200` | Array JSON directo de `{id, name, role}`, sin envoltorio |
| Unicidad y orden | Un elemento por `User.id`, orden estable por `name` y después `id` |
| Sin coincidencias | `200 OK` y `[]`, nunca `404` (con un ADMIN solicitante activo debería haber al menos un ADMIN elegible) |
| Campos excluidos | `email`, `isActive`, `areaIds`, contraseñas, hashes, sesiones, tokens, fechas y relaciones internas |

El campo `isActive` **no es necesario en esta respuesta pública**, porque todos los candidatos listados tienen `isActive=true` por definición. Esto no elimina la necesidad de que el puerto interno de Documentos lo exponga.

**Alcance vigente:** Equipo C ratificó que el listado de candidatos es exclusivo de `ADMIN`. El endpoint no reemplaza la resolución de referencias históricas, que C incorporará a los DTO autorizados de Documentos.

  {"id":"0b000000-0000-4000-8000-000000000003","name":"Elena Empleada de Ventas","role":"EMPLOYEE"},
  {"id":"0b000000-0000-4000-8000-000000000005","name":"Emilio Empleado de Operaciones","role":"EMPLOYEE"},

Los UUID y nombres son fixtures; los resultados suponen áreas y usuarios activos. No representan una respuesta observada. Si se consulta solo el área de Ventas, se esperaría a la ADMIN y a los usuarios activos relacionados con Ventas, no a los pertenecientes únicamente a Operaciones.

## 5. Errores esperados al implementar

| HTTP | Condición | Criterio |
|---|---|---|
| `200 OK` | Solicitante autorizado y áreas válidas | Array de candidatos, incluso `[]` |
| `400 Bad Request` | Faltan áreas; algún ID es inexistente o inactivo | **Acordado con C**; validar toda la selección antes de responder candidatos |
| `400 Bad Request` | UUID mal formado, CSV, parámetros no soportados | Validación del contrato propuesto |
| `401 Unauthorized` | Token ausente/inválido o cuenta solicitante desactivada | No revelar candidatos |
| `403 Forbidden` | Solicitante autenticado sin rol autorizado | Depende de ratificar la propuesta de lectura ADMIN |
| `404 Not Found` | Ningún candidato encontrado | **No corresponde**; usar `200 []` |
| `503 Service Unavailable` | Infraestructura no disponible | Objetivo a probar; no convertir el fallo en `200 []` |

Formato esperado de errores: convención Nest (`statusCode`, `message`, `error`) sin detalles sensibles. El endpoint todavía no existe; estos códigos no son pruebas HTTP realizadas.

## 6. Personas inactivas y referencias históricas: acuerdo con C

Matías confirmó que **no deben admitirse responsables inactivos en asignaciones nuevas**, pero los documentos existentes deben conservar sus referencias. También aclaró que un documento de responsable inactivo cuya revisión esté vencida no desaparece: el `ADMIN` continúa viéndolo en «Por revisar».

Para hacer viable esta regla, el Equipo A debe coordinar con C la ampliación del **puerto interno** de Documentos, no de la respuesta HTTP de candidatos:

```typescript
// Contrato interno esperado tras coordinar su modificación con C;
// NO está implementado en la revisión documental.
export interface DirectoryUser {
  id: string;
  role: Role;
  areaIds: string[];
  isActive: boolean;
}
```

La implementación Prisma deberá devolver el valor vigente de `User.isActive`; **no** filtrar silenciosamente a los usuarios inactivos con `null`, porque C necesita distinguir «usuario histórico existente pero inactivo» de «usuario inexistente». C implementará la validación en Documentos diferenciando **nueva asignación** de **conservación de la referencia anterior**.

Un `ownerId` elegido desde el listado puede volverse inactivo antes de guardar: la API de Documentos debe volver a comprobar el estado en ese momento. La política de autorización de consulta de documentos permanece en el backend.

### Dependencia relevante del frontend

`OwnerField` actualmente limpia el responsable si ya no aparece entre los candidatos nuevos. Por eso, al editar documentos históricos, **no se debe tratar el directorio de candidatos como el directorio de nombres** ni borrar un responsable histórico sin que el usuario decida reasignarlo. El diseño de ese flujo se coordina con C; no se cambia en A-06.3.

A-06.4 acordó resolver nombres y estados históricos desde los DTO autorizados de Documentos, sin agregar `GET /api/users/names`. Su implementación corresponde a Equipo C.

## 7. Criterios de aceptación de implementación (A-12)

- [ ] Solicitante autorizado y activo: una o varias áreas activas producen los candidatos activos correspondientes más los ADMIN activos.
- [ ] Parámetros `areaIds` repetidos: unión de resultados sin duplicados; IDs repetidos no duplican personas.
- [ ] La respuesta tiene exactamente `{id,name,role}`, no expone `isActive`, `email` ni `areaIds`.
- [ ] Usuarios inactivos, incluso ADMIN, no son candidatos.
- [ ] Relaciones solo con áreas inactivas no convierten a un usuario en candidato por esa relación.
- [ ] `areaIds` ausente, UUID mal formado, CSV, área inexistente, área inactiva o query ajena: `400`.
- [ ] Sin credenciales: `401`; sin rol autorizado: `403` si se mantiene la regla ADMIN.
- [ ] Orden estable por nombre e ID; si no hay filas: `200 []`.
- [ ] Infraestructura indisponible: error controlado, nunca resultado falso vacío.
- [ ] La web conserva `listOwnerCandidates(areaIds)` sin depender de campos adicionales.
- [ ] Documentos valida nuevamente la actividad del responsable antes de guardar; un valor enviado manualmente no elude la regla.
- [ ] Los documentos históricos conservan sus referencias y permanecen visibles según sus permisos, incluidos los pendientes de revisión para ADMIN.

Estos casos son **pendientes de ejecución**. Esta actualización es exclusivamente documental.
