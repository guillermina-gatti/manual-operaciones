**Proyecto:** PispIAr — IntegrarTEC 2026
**Equipo:** A — Seguridad y Plataforma
**Microtarea:** A-06.2, exclusivamente definición documental
**Fecha de revisión:** 30/10/2026
**Base de código revisada:** `develop@d452a0d85eea1b3d33bf92e572a963f9be87ac31` (PR #14 de A-06.1 fusionado)
**Estado de este documento:** propuesta concreta para revisión y acuerdo interequipos; **no** demuestra que el endpoint exista ni sustituye su implementación.

## 1. Objetivo y alcance

Definir un contrato HTTP pequeño y verificable para que las pantallas de documentos puedan consultar nombres de áreas y, en los formularios administrativos, seleccionar áreas habilitadas. La API todavía **no** expone una ruta de áreas en `AppModule`; el frontend utiliza `createFakeAreasDirectory()`.

**Incluye:** método y URL, roles, filtrado, estructura de respuesta, errores y casos de prueba para cuando se implemente (bloque A-11).
**No incluye:** crear controlador, modificar Prisma, cambiar el directorio web, exponer altas/bajas, cambiar el puerto backend `documents/ports/areas-directory.ts`, ni modificar módulos de B/C.

## 2. Contrato público propuesto

| Aspecto | Definición candidata |
|---|---|
| Método y ruta | `GET /api/areas` |
| Requiere autenticación | Sí: `Authorization: Bearer <accessToken>`; usuario existente y activo |
| Roles permitidos para **lectura de nombres** | `ADMIN`, `SUPERVISOR`, `EMPLOYEE` |
| Filtro fijo del servidor | Solo `Area.isActive = true` |
| Áreas devueltas | Todas las áreas **activas**, sin filtrar por áreas asignadas al solicitante |
| Query params | Ninguno admitido; las consultas con parámetros no soportados deben responder 400 |
| Body de la petición | Ninguno |
| Respuesta 200 | **Array JSON directo** de `{ "id": string (UUID), "name": string }` |
| Orden | Ascendente por `name`; para empates, por `id`, de manera estable |
| Sin áreas habilitadas | `200 OK` con `[]`, no 404 |
| Campos prohibidos | `isActive`, timestamps, usuarios asociados, correos, roles, contraseñas, hashes y metadatos no pedidos |

**Justificación de permisos.** `AreasDirectory.listAreas()` es usado tanto por `UploadDocumentForm` (solo ADMIN) como por `DocumentList` y `DocumentDetail` (todos los roles autenticados que pueden ver documentos). Restringir `GET /api/areas` a ADMIN rompería la resolución de nombres de áreas en las pantallas de los otros roles cuando el frontend cambie de fixtures a HTTP. Esto propone **lectura del catálogo de nombres** para usuarios autenticados, no administración de áreas ni autorización de acceso a recursos.

El listado no concede permisos: los servicios de Documentos y Procedimientos siguen filtrando por rol, pertenencia a áreas, estado del recurso y reglas propias. Esta propuesta supone que **los nombres del catálogo de áreas no son información confidencial entre empleados autenticados**; como expone nombres de áreas ajenas, el equipo debe validar esa clasificación antes de aceptar el contrato. Si se consideran sensibles, habrá que acordar con C una solución diferente para resolver nombres en documentos. La matriz actual limita **crear o modificar áreas** a ADMIN; el permiso de lectura de nombres se registra aquí como decisión propuesta que requiere validación de los consumidores.

## 3. Ejemplos de consumo y respuestas

```http
GET /api/areas HTTP/1.1
Authorization: Bearer <token-válido>
Accept: application/json
```

**200 OK — ejemplo ilustrativo:**

```json
[
  {"id": "0a000000-0000-4000-8000-000000000002", "name": "Operaciones"},
  {"id": "0a000000-0000-4000-8000-000000000001", "name": "Ventas"}
]
```

**200 OK — sin áreas activas:** `[]`. Son ejemplos de contrato, **no** peticiones ejecutadas.

### Errores previstos para la implementación

| HTTP | Condición | Criterio |
|---|---|---|
| `200 OK` | Usuario activo con cualquier rol permitido; la base responde | Array directo, incluso vacío |
| `400 Bad Request` | Se envían parámetros no admitidos, p. ej. `?includeInactive=true` | No interpretar ni permitir solicitudes de áreas inactivas |
| `401 Unauthorized` | Sin Bearer, token inválido/vencido o usuario inactivo | Los guards existentes validan identidad vigente |
| `403 Forbidden` | **No previsto** para un usuario activo con rol válido en esta versión, porque los tres roles están autorizados | Si se cambia el conjunto de roles, documentar el 403 y revisar consumidores |
| `404 Not Found` | **No corresponde** a un listado; si no hay registros devuelve 200 con `[]` | No confundir vacío con inexistente |
| `503 Service Unavailable` | Base de datos temporalmente indisponible | **Comportamiento deseado** por revisar/probar en A-11, incluso si el fallo ocurre durante el guard; no garantizarlo como comportamiento actual |

Formato de errores esperado: la convención de Nest que consume el cliente web (`statusCode`, `message`, `error`), sin filtrar detalles de infraestructura. No devolver listas parciales ni transformar errores de DB en `[]`.

## 4. Distinción importante: área activa vs referencia histórica

La regla de esta consulta es **solo activas** para que el selector no permita nuevas asignaciones sobre áreas deshabilitadas. Sin embargo, `DocumentList` y `DocumentDetail` también usan el catálogo para traducir `areaId` a nombre. Si un documento antiguo conserva un área actualmente inactiva, esta ruta **no** devolverá su nombre y el frontend podría mostrar `—`.

**Decisión pendiente con Equipo C:** definir cómo visualizar nombres históricos de áreas que el usuario ya está autorizado a ver, sin reactivar el área ni abrir una consulta global de datos históricos. Posibles soluciones futuras: aportar el nombre en una respuesta autorizada de documento, o acordar un mecanismo de resolución restringido. **No** se elige ni implementa esa solución en A-06.2.

Esta regla de lectura tampoco modifica `PrismaAreasDirectory.findExistingIds()`: dicho puerto del backend de Documentos responde a otra finalidad y tiene una decisión sobre inactivos pendiente desde A-06.1.

## 5. Casos de aceptación para cuando se implemente A-11

- [ ] `ADMIN` activo obtiene 200 con todas las áreas activas.
- [ ] `SUPERVISOR` activo obtiene 200, sin error 403 por el mero hecho de leer nombres.
- [ ] `EMPLOYEE` activo obtiene 200, sin error 403 por el mero hecho de leer nombres.
- [ ] Las áreas con `isActive=false` no aparecen, aun si el solicitante es ADMIN.
- [ ] La respuesta contiene **solamente** `id` y `name`, en orden estable.
- [ ] Base sin áreas activas: 200 y `[]`.
- [ ] Sin token, token inválido o usuario inactivo: 401.
- [ ] Parámetro no soportado: 400, sin alterar el filtrado fijo de áreas activas.
- [ ] Falla de DB: error controlado, nunca lista vacía que oculte el fallo; comprobar mapeo esperado a 503.
- [ ] Un usuario no gana acceso a documentos de otras áreas por haber consultado este endpoint.
- [ ] No se rompió la firma web `AreasDirectory.listAreas(): Promise<Area[]>`.

**Pruebas ejecutadas en A-06.2:** inspección estática de archivos de `develop` y revisión documental. No se ejecutaron tests HTTP, Jest, Vitest ni build; el endpoint todavía no está implementado.
