## 1. Objetivo y límites

Permitir que el frontend traduzca `areaId` a nombre en documentos, incluidos los que conservan referencias a áreas desactivadas, y que distinga cuáles son elegibles en formularios de nuevas asignaciones. La lectura del catálogo no otorga acceso a documentos ni permite administrar áreas.

**Incluye:** método y ruta, permisos, formato exacto, orden, errores, reglas de inactivos y criterios para implementar A-11.
**Fuera de alcance:** crear controlador o servicio HTTP, modificar Prisma, sustituir los fixtures, modificar la política de Documentos (Equipo C), crear un endpoint para administrar áreas o resolver los contratos de usuarios (A-06.3/A-06.4).

**Estado del código revisado:** `apps/api/src/app.module.ts` todavía no registra `GET /api/areas`; `apps/web/lib/directory/index.ts` utiliza `createFakeAreasDirectory()`. La interfaz web `Area` solo incluye `id` y `name`; deberá ampliarse al implementar el consumo de `isActive`.

## 2. Contrato HTTP acordado

| Aspecto | Definición |
|---|---|
| Método y ruta | `GET /api/areas` |
| Autenticación | Obligatoria, `Authorization: Bearer <accessToken>`; cuenta existente y activa |
| Roles con permiso de lectura | `ADMIN`, `SUPERVISOR`, `EMPLOYEE` |
| Alcance del catálogo | **Todas** las áreas existentes, con `isActive=true` **y** `isActive=false` |
| Alcance por pertenencia | Sin filtrar por las áreas asignadas al usuario solicitante |
| Parámetros de consulta | Ninguno; cualquier query param no admitido devuelve `400` |
| Cuerpo de petición | Ninguno |
| Respuesta `200 OK` | **Array JSON directo** de objetos `{id, name, isActive}`; sin envoltorio |
| Tipos | `id`: UUID string; `name`: string; `isActive`: boolean |
| Orden | `name` ascendente y, en caso de empate, `id` ascendente |
| Catálogo completamente vacío | `200 OK` con `[]` |
| Campos excluidos | Contraseñas, hashes, correos, usuarios asociados, sesiones, timestamps y metadatos internos |

**Permiso acordado con C.** Matías confirmó que cualquier usuario autenticado puede consultar los nombres de las áreas y pidió incorporar explícitamente su estado. Este endpoint ofrece solo un catálogo organizacional: la API de Documentos continúa validando acceso por rol, pertenencia y reglas del recurso. **No** debe usarse este listado como prueba de autorización para leer documentos de otras áreas.

### Ejemplo ilustrativo de respuesta

```http
GET /api/areas HTTP/1.1
Authorization: Bearer <access-token>
Accept: application/json
```

```json
[
  {
    "id": "0a000000-0000-4000-8000-000000000002",
    "name": "Operaciones",
    "isActive": false
  },
  {
    "id": "0a000000-0000-4000-8000-000000000001",
    "name": "Ventas",
    "isActive": true
  }
]
```

Los nombres, UUID y estados del ejemplo son ilustrativos: **no** representan una respuesta HTTP observada ni el estado de los fixtures actuales.

## 3. Reglas de negocio: lectura histórica frente a nuevas asignaciones

La distinción central es entre **mostrar un área ya vinculada** y **asignarla ahora**.

| Escenario | Comportamiento acordado |
|---|---|
| Documento existente asociado a un área que ahora está inactiva | Conservar el `areaId` y mostrar su nombre seguido de ` (inactiva)` |
| Crear documento con un área inactiva | Rechazar la asignación con HTTP `400`, igual que un área inexistente |
| Cambiar áreas de un documento y **añadir** un área inactiva | Rechazar el cambio con HTTP `400` |
| Cambiar áreas conservando un área inactiva **que ya estaba asignada** | Permitir conservar esa referencia histórica; no reactivarla ni exigir quitarla |
| Elegir áreas en un formulario nuevo | Ofrecer como seleccionables solo las áreas con `isActive=true` |
| Consultar el catálogo sin ninguna área activa, pero con áreas inactivas | Devolver las áreas inactivas con `isActive=false`; **no** devolver `[]` por ese motivo |
| Consultar un catálogo sin registros de ningún estado | `200 OK` con `[]` |

**Responsabilidad de cada equipo.** El Equipo A entrega los estados en el catálogo. El Equipo C, responsable de Documentos, implementa la validación del lado del servidor para cargas y cambios de áreas, conservando las referencias históricas existentes. El frontend debe filtrar opciones de nueva asignación, pero **el control de seguridad y reglas de negocio no puede depender del frontend**.

**Puerto interno existente:** `apps/api/src/documents/ports/areas-directory.ts` expone `findExistingIds(ids)` y el adaptador Prisma solo comprueba existencia, no estado. **No cambiar unilateralmente la firma ni asumir que ya rechaza áreas inactivas.** Equipo C debe definir o adaptar su validación de nuevos vínculos sin invalidar los anteriores; coordinar el acceso al estado `isActive` en ese flujo.

**Dependencia frontend:** `apps/web/lib/directory/areas-directory.ts` define actualmente `Area={id,name}`. En A-11/T28 o en una tarea coordinada, ampliar a `Area={id,name,isActive}` y actualizar fakes y consumidores para mostrar la etiqueta histórica y restringir la selección. Esto **no** se hace en esta revisión documental.

## 4. Errores HTTP previstos para A-11

| Estado | Condición | Criterio |
|---|---|---|
| `200 OK` | Cuenta autenticada y activa, con cualquiera de los tres roles | Array completo ordenado; `[]` solo si no existe ninguna área |
| `400 Bad Request` | Parámetros de consulta no admitidos, como `?active=true` o `?includeInactive=false` | La ruta no ofrece filtrado configurable por estado |
| `401 Unauthorized` | Falta Bearer, JWT inválido o vencido, o cuenta solicitante inactiva | Usar el guard actual de autenticación |
| `403 Forbidden` | No previsto para ninguno de los tres roles autenticados y activos | No convertir lectura del catálogo en permiso exclusivo de ADMIN |
| `404 Not Found` | No corresponde al listado | Sin filas: `200 []` |
| `503 Service Unavailable` | Falla temporal de base de datos | **Comportamiento objetivo que deberá verificarse**, incluso durante la autenticación; no transformar el fallo en `200 []` |

Los errores deben seguir la convención de Nest (`statusCode`, `message`, `error`) sin filtrar información de infraestructura. La validación de áreas en **altas/cambios de documentos** que devuelve `400` corresponde al módulo de Documentos, no a un `GET /api/areas` de solo lectura.

## 5. Criterios de aceptación futuros (A-11 y coordinación con C)

### Endpoint `GET /api/areas` — Equipo A

- [ ] `ADMIN`, `SUPERVISOR` y `EMPLOYEE` activos reciben `200` y el mismo catálogo de nombres/estados.
- [ ] Se incluyen áreas activas e inactivas, sin filtrar por pertenencia del solicitante.
- [ ] Cada elemento tiene **exactamente** `id`, `name` e `isActive`; `isActive` es booleano.
- [ ] Las áreas se ordenan por `name`, luego por `id`.
- [ ] Sin áreas de ningún estado: `200 []`.
- [ ] Con solo áreas inactivas: `200` con esos registros, **no** `[]`.
- [ ] Sin token, token inválido/vencido o cuenta inactiva: `401`.
- [ ] Parámetros no admitidos: `400`.
- [ ] Error de infraestructura: error controlado (objetivo `503`), nunca catálogo vacío simulado.
- [ ] La lectura del catálogo no permite acceder a documentos no autorizados.

### Integración con Documentos y frontend — coordinación A/C

- [ ] La interfaz web `Area` y sus implementaciones admiten `isActive` sin romper consumidores.
- [ ] Un documento con área inactiva conserva y muestra `Nombre (inactiva)`.
- [ ] Los selectores de **nuevas** asignaciones excluyen áreas inactivas.
- [ ] La API de Documentos devuelve `400` al crear o agregar un área inexistente o inactiva.
- [ ] Al modificar áreas se puede conservar una referencia inactiva preexistente.
- [ ] Los cambios de áreas no alteran retroactivamente los permisos ni exponen documentos ajenos.

Ninguno de estos tests se ejecuta en esta microtarea documental. Son obligaciones de implementación y validación posteriores.
