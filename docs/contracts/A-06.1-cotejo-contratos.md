## 3. Diferencias y preguntas que se registran, pero NO se resuelven ahora

1. **Usuarios inactivos en el puerto de Documentos.** `PrismaUsersDirectory.findById` no filtra `User.isActive`. En cambio, `JwtAuthGuard` sí rechaza al solicitante inactivo. El validador `DocumentWriteSteps.assertOwnerCanSeeDocument` consulta el puerto para aceptar a un responsable sin comprobar `isActive`. **Pregunta:** ¿un usuario inactivo debe poder quedar asignado como responsable nuevo, o solo conservar su referencia histórica? Se necesita acuerdo con C antes de cambiar el puerto/validación. No afirmar que el guard esté fallando: son recorridos distintos.
2. **Áreas inactivas en validación documental.** `PrismaAreasDirectory.findExistingIds` consulta existencia por ID, sin `isActive`, y `DocumentWriteSteps.assertAreasExist` usa ese resultado. Esto es compatible con el nombre literal del puerto, pero **no garantiza** la regla general del documento `users-areas.md` de usar solo áreas habilitadas en nuevas asignaciones. **Pregunta:** ¿qué flujo debe excluir áreas inactivas y cuál debe conservar referencias históricas? Resolver con C; no modificar el puerto público sin acuerdo.
3. **Identidad después de refresh.** El backend responde `accessToken` sin `user`; la sesión de desarrollo recupera el nombre/rol desde fixtures. Falta acordar cómo restaurará identidad la sesión web real (A-06.5/A-07). **No** se define ni implementa `GET /api/auth/me` aquí.
4. **Endpoints web todavía no presentes.** Las interfaces de T28/T29 existen y están conectadas a fakes; no hay `GET /api/areas` ni `GET /api/users?areaIds=...` registrados en el `AppModule` revisado. La selección de permisos, parámetros y respuesta definitiva corresponde a A-06.2/A-06.3 y los bloques posteriores. `getNames(ids)` no tiene todavía un contrato HTTP seguro acordado (A-06.4).
5. **Desactualización de decisiones del documento base.** `users-areas.md` pregunta si `Role` será enum y si habrá unicidad del nombre de área. En Prisma ya hay `enum Role` y `Area.name @unique`; **no** hay evidencia en este cotejo de una política de normalización de nombres. Registrar el hecho sin editar la decisión original ni declararla aprobada.
6. **Planes históricos vs estado real.** El plan 001 menciona adaptadores/guards simulados y ausencia inicial de PrismaService; los adaptadores reales y los guards públicos ya están cableados. El plan 002 registra T28–T30 como bloqueados; siguen pendientes en las conexiones de frontend inspeccionadas. No volver a implementar lo que ya existe en backend.

## 4. Ejemplos de contrato HTTP que **ya** existe

Ejemplos ilustrativos de formato, extraídos de `auth.controller.ts`. No son capturas de ejecución ni nuevos compromisos para la API.

```http
POST /api/auth/login
Content-Type: application/json

{"email":"usuario@ejemplo.test","password":"<contraseña de prueba>"}
```

Respuesta 200 documentada: `{"accessToken":"<JWT>","user":{"id":"<UUID>","name":"Usuario","email":"usuario@ejemplo.test","role":"EMPLOYEE"}}` y cookie refresh `httpOnly`.

```http
POST /api/auth/refresh
Cookie: refreshToken=<cookie opaca>
```

Respuesta 200 documentada: `{"accessToken":"<JWT nuevo>"}` y rotación de cookie. La respuesta **no incluye** `user`.

```http
POST /api/auth/logout
Cookie: refreshToken=<cookie opaca>
```

Respuesta 200 documentada: `{"revoked":true}` o `{"revoked":false}`, según si se revocó una sesión.

Los códigos documentados de login incluyen 400 (entrada inválida), 401 (credenciales), 429 (límite de intentos) y 503 (control de tasa no disponible). En esta microtarea **no** se probaron respuestas reales ni se fijaron códigos nuevos para endpoints futuros.
